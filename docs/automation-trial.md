# 自动化对话试用

本轮试用在飞书原话题中进行。用户用自然语言交代任务，Agent 从对话提取定义、调用后台创建，并将创建结果、产出和需要人处理的问题写回飞书。用户不需要访问独立网站、填写表单或输入任务 ID。2026-10-27 根据原交办人的纠正，已关闭前一版网页试用入口及其独立服务；三份验收样例和后台代码保留，没有迁移或更改原有自动化。

2026-10-28，普通自动化已接入“卡片确认启用 → 独立固定执行 Session → 原任务话题承接结果和修改 → 卡片停止”。复用原生 Schedule／Trigger、Run 和来源投递；确认记录只保存定义、本人操作和卡片回执，不另建调度器。该入口适用于飞书已核人类交办，日报单独维护，已有任务不自动迁移。新代码的隔离验证覆盖原生存储、SDK 回调、重复投递和停止；飞书服务端回调与用户客户端的自然使用仍须分别以实际记录核验。周度监管另议。

## 普通自动化的默认创建流程

2026-10-28，原交办人在比较会话模式后确认：**后续新增的普通自动化，每条建立一个独立固定 Session，每次触发继续在这个 Session 执行。** 这个 Session 同时承接人的纠正、任务状态与故障修复。它是实际执行会话，不只是另设一个讨论入口。此项是 Agent 承接新自动化时采用的创建规则；底层 API 的显式策略仍保留，不批量迁移已有任务。

日报单独维护，沿用日报项目自己的执行与上下文方案。其他任务默认采用上述方式；每轮确实需要大量独立材料、执行间没有承接价值的任务，可以根据实际需要选择新上下文并说明理由，不按一个未经验证的“复杂度阈值”自动切换。已有工作中的一次延时接续仍回原执行会话，不为它另建一条自动化。确定性的提醒、搬运优先复用现有代码能力，需要理解或判断时才调用模型。

Agent 创建时使用已接好的入口，不手工拼装一条提前启用的 Schedule：

1. 保留原交办会话、实际人类输入及授权，核对是否已有任务。将任务定义提交到 `POST /api/automation-confirmations`。后台从该输入解析已核身份、Bot 和原话题，不接受调用者另填接收者或确认人。
2. 后台只创建承接任务所需的独立 Session 和 **paused** 原生任务，默认 `fixed_session`；来源仍指向原交办会话。不会复制来源聊天，也不启动模型。原话题收到“待确认 · 尚未启用”卡片，详情默认收起。
3. 原交办人点击“确认启用”后，连接器在同群创建专属任务话题。消息回读成功、Session 绑定和结果投递地址保存后，才启用原生任务。原卡片留下任务入口，任务卡留下原交办入口。重复点击和重试复用已有任务、会话与卡片。
4. 以后每次触发在这个 Session 执行，结果沿原生投递通路回任务话题。这里只启用未来触发，不附带“立即运行”。讨论、示例或维护本流程都不授权创建真实业务自动化。

服务身份接口的数据示例如下，字段须替换为当次真实交办；这是协议示例，不是要创建的任务：

```json
{
  "key": "同一条交办中该任务的稳定键",
  "sourceSessionId": "原交办Session",
  "sourceRequestId": "实际人类输入ID",
  "kind": "recurring",
  "title": "任务名称",
  "text": "明确的执行内容、输入位置、输出与接收方、约束及必要SOP",
  "cron": "0 8 * * *",
  "timezone": "Asia/Shanghai",
  "output": "结果位置与接收方，常规结果回专属任务话题",
  "cost": "暂无实测",
  "details": "可选：负责人、适用范围、异常处理与原始依据"
}
```

间隔任务用 `everySeconds` 替换 cron/timezone；一次性任务用 `kind: "one_time"` 和未来的 ISO `scheduledAt`。用 `remotelab api POST /api/automation-confirmations --body-file <JSON路径>` 提交，`GET /api/automation-confirmations/:key` 回读 `phase`、原生任务、执行 Session 和真实入口。请求键会与原输入绑定；改动未确认的定义须取消旧任务并发新卡。`/action` 与 `/receipt` 仅供已核连接器回调，不得由 Agent 伪造人的点击。该确认是交办人要求的一次启用动作，不在每轮自动化前追加确认。

代码：`chat/automation-confirmations.mjs`、`connectors/feishu/automation-cards.mjs`。回执分别保存在实例 `automation-confirmations/` 和连接器 `automation-cards/`；发送结果不明时保留发送栅栏并沿现有投递问题流程核查，不盲目重发。底层 `/api/schedules`、`/api/triggers` 的显式用法仍保留；本流程不设置 `automationHome: true`。

后续每轮保留当前规则、必要状态和最近有效结论，完整日志留在记录中按需读取。上下文压缩沿所选 Harness 的原生能力；固定 Session 不等于每次主动读取全部历史，也不等于闲置时持续消耗模型。人的纠正若影响未来执行，须同步到任务正文／实际配置或任务所引用的现行规则，回读确认并说明生效范围；不能仅回复“记住了”。已被接纳的执行是否需要调整，按纠正的实际含义处理，不假定会被后续配置自动改写。

暂停、恢复和停止沿原生任务生命周期处理并核对实际状态。卡片停止会取消未来触发并请求结束已经接纳、尚未终态的自动化 Run；“请求停止”不表示外部训练、设备等业务作业也已结束，相关作业仍按其实际控制和授权处理。故障继续关联到原执行与修复记录，独立观察器仍负责发现异常。

## 创建时

Agent 负责从原交办补齐已知信息，只问真正影响执行的缺项。任务正文与详情保留目的、输入、输出、接收方、负责人、适用范围、异常处理和必要 SOP。成本给有依据的大概用量或费用；没有依据就说明暂无实测，不代用户设置预算、限额或费用暂停。

卡片区分“待确认”“正在建立任务话题”“已启用”“已停止”，不能把待确认说成已启用。展示样例时明确“示例，未创建任务”。卡片直接发到原飞书话题，不用跳转链接代替交付；详情按钮展开或收起，并在刷新、完成和续接时保持人的选择。

| 位置 | 内容 |
| --- | --- |
| 常显摘要 | 任务名称、真实创建状态、执行时间、输出与接收方、预计成本 |
| 默认折叠的“任务详情与异常处理” | 目的、输入、输出、接收方、负责人、必要的生效对象／SOP 范围和日期、监管与预警；紧密相关的字段可以合并 |
| 操作入口 | 待确认时“确认启用／取消”，启用后“停止任务”；保留刷新状态与任务话题入口 |

停止先写入后台，再由持久投递刷新卡片；刷新失败不撤销停止。飞书返回卡片更新过期错误 230031 时，在原话题补一张最新卡，继续指向同一任务与 Session，不增加定时续期。已停止任务不能从旧卡重新启用。旧卡的按钮回调若未到达服务器，不能假装操作成功；人可在任务话题说“停止此自动化”，Agent 按原生任务 ID 取消后续触发并按需要取消当前 Run，回读后回复。卡片超期后的客户端回调仍以实际可用性为准。

验证：`node scripts/run-with-clean-instance-env.mjs node tests/test-automation-confirmation-cards.mjs`。隔离测试使用真实原生任务与投递存储、服务鉴权路由及 SDK 事件归一化，飞书消息 API 使用夹具；覆盖本人、租户、群与消息归属、重复确认、话题绑定后启用、固定会话复用、定义变化拒绝启用、一次性与循环任务停止、当前 Run 取消请求、重启回执恢复和旧卡更换。它不代替线上真人点击和飞书客户端验收。

任务细节和底层重试记录保存在后台。用户在同一话题说“暂停”“修改时间”“继续”，Agent 找到原任务后操作，再用一句话回报实际结果；不让用户管理后台编号。修改时只说明变化及何时生效。

## 运行后的文字

| 情况 | 飞书中的输出 | 后台动作 |
| --- | --- | --- |
| 正常完成 | 直接给约定结果及必要来源／附件 | 保留结果和投递回执；不重复创建时的任务定义 |
| 没有值得推送的新内容 | 按该任务原约定决定是否静默 | 记录本轮正常检查，不能把执行失败当成“无更新” |
| 发生影响交付的异常，Agent 能处理 | 说明具体异常、受影响的结果、正在采取的处理；仅在这些信息对用户有用时发送 | 先定位原因，按 SOP 修复；瞬时故障有限重试，持续失败不能只顺延 |
| 需要人介入 | 说明未完成的事、实际已尝试的修复，以及需要谁做的一个具体动作 | 保留原问题，接收人在原话题的补充后继续；不要求额外点击“确认接手” |
| 已恢复 | 如先前已向人预警，说明问题如何解决以及本轮结果如何处理 | 核对结果时效；仍有效才补送，过期就说明跳过，不补发旧提醒 |

通知本身失败时处理投递，不重新生成已经完成的业务结果。投递成功不等于人已读；交给 Agent 的消息被接纳不等于其下游任务已完成。用户侧只呈现影响理解和下一步的状态。

## 会话与监管的现状核对

2026-10-27 核对现行实现与实例记录：应区分固定主会话与执行会话。已有显式选择的自动化可创建固定主会话（`automationHome: true`），用于讨论、查询、修改和关联历次执行；它只带本任务交接信息，不复制来源对话。后台仍按原策略执行，主会话不会在每轮执行时另跑一次模型。详细契约见 [Task Center：Stable automation home](task-center-v1.md#stable-automation-home-explicit-opt-in)。该能力不是全部自动化的默认行为。

创建 Schedule／Trigger 先登记调度，执行会话在触发时解析或创建。`chat/triggers.mjs` 的 `ensureExecutionSession` 支持每轮新建、按日复用、固定会话，以及沿已绑定的飞书话题复用。项目巡检已有固定主会话，其同日晨间／傍晚执行复用另一条执行会话，次日更换执行会话。因此“有固定入口”不等于“每次执行继续同一模型上下文”。主会话中的交谈也不会自动全文注入各轮执行；执行使用任务定义及按需读取的关联记录。会话闲置不持续调用模型。

现行 `chat/monitoring-recovery.mjs` 将自动化故障关联到失败执行的会话，在该会话提交修复请求；实例中已有原执行和修复 Run 使用同一会话的记录。发现异常、登记故障及核对修复结果由独立观察器负责，不能依赖可能已卡住的执行 Agent 自己发现异常。试验引擎同样在每轮执行会话里继续修复，但新周期会新开执行会话。

仍需调整的一处现行行为：补救器在发现任务已有更新执行时可能取消旧补救，没有要求新执行已经解决旧故障。后续把监管处理归入同一自动化任务时，应保留故障与执行轮次的关联，按实际恢复证据结束故障。上述是 2026-10-27 的现状核对，未更改既有会话复用、监管或调度配置；后续普通新任务的选择以 2026-10-28 确认的默认创建流程为准，日报仍单独维护。

## 保留的后台试验

源码在 `automation/trial/`，原页面在 `static/automation-trial/`，均保留供后续复用；现行试用不再要求用户进入页面。样例状态在实例私有的 `automation-trial` 目录。原有 Schedule、Trigger 及监控恢复台账未被本试验改写。

现有引擎通过原生 Session／Run 执行。执行失败或没有有效结果时最多两轮 Agent 诊断修复，明确缺少人工输入时直接转人工；新周期不覆盖原问题。监管通路暂不可读时保留原运行，恢复后接着观察。结果交接依照任务 SOP，不追加一套通用业务审核。成本不形成限制。

验证命令：`node scripts/run-with-clean-instance-env.mjs node --test tests/test-automation-trial.mjs`。13 项状态测试使用隔离夹具；真实样例另验证了正常结果、人工依赖、受控故障修复和 Agent 接收。它们不证明飞书自动通知已经接通。重新启用任何服务或定时任务应以实际试用交办为准，不能仅因本文存在就启动。
