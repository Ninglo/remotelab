# HR access policy

Delegate with: “Use the current accepted human request to inspect or update HR access. Read the authoritative policy, preserve existing identity bindings, make the requested role or scope change with its version and reason, and verify the new policy. Do not issue platform credentials or reopen paused interviewers.”

HR permissions and RemoteLab platform administration are independent. The deployed business service owns one versioned policy row and an append-only change audit. A Git policy file is the bootstrap seed, not a second live authority. The runtime guard's `hrPolicyRegistry` points to that service with an instance-local credential path; no credential belongs in source or model output. `hrInstance`, `hrRestrictedRuntime` and `hrEnforceAfter` identify the deployment and shared-browser cutover.

The policy binds people to authenticated app/tenant/route identities or personal browser identity pairs. An authenticated connector's sender is authoritative; a name or claimed actor in message text is not. Shared browser bindings have only the fixed collaboration projection and cannot infer a candidate owner. Pre-cutover shared histories remain inaccessible to that shared identity.

HR1 manages existing users' roles and information scopes. Only the separately designated owner adds or removes assistant users or completes their verified Feishu identity binding. HR2 has full HR business access without access administration. Recruiting collaborators see shared job information and handle their own candidates. Interviewers see assigned candidates and submitted earlier feedback, and submit only their own completed-interview review. Bosses have full information access and personal interview feedback rights, without general HR business writes. Membership in an app's scheduling directory does not activate assistant access.

`remotelab hr-access show` reads the current policy using the accepted human Run. `change --file <json>` accepts `action`, `target`, `expectedVersion`, `reason`, and the matching `roles`, `scope` or `subject` payload. The server derives the actor and audit reference; service credentials must reference an active, original human request. The business service checks permissions again, commits with version comparison, updates the legacy recruiting-membership projection, and records the audit atomically. Retry the same request after uncertain results; never edit runtime allowlists to simulate success.

For an already registered person whose Touma account has just become available, `action:bind` accepts one verified `binding` with `kind:feishu`, `route:muka-hr`, the Touma app and tenant, and that app's `openId`. Verify the enterprise identity against existing evidence first. The operation only completes a missing binding; it preserves roles, rejects identities attached to another person, and cannot replace a previously bound account or issue browser credentials. Reopening an existing paused interviewer uses owner-authorized `action:add` with the existing target and no new subject.

`remotelab hr-access feedback --file <json>` takes `candidateId`, `interviewId`, `text`, optional `score` and `append`. The service verifies the actual confirmed, uncancelled interview assignment and start time. It stores the person's review separately from the hiring outcome, preserves others' reviews, and deduplicates delivery by source message. UI and notification schedules are separate work; this command does not enable them.

Policy reads refresh at admission, protected-source reads and connector delivery. A registry failure denies protected work. On a general-purpose instance, unrelated technical requests can continue without HR rights. Restricted HR browser instances fail closed for unavailable policy checks. WebSocket delivery applies the same session visibility checks as HTTP.

This implements application and authenticated entry boundaries. It does not isolate root/sudo, arbitrary filesystem tools, content already in an old model context, or external copies. Those remain subject to the current execution rules and require separate OS/tool isolation to become hard boundaries. Do not report documentation updates as universal enforcement.

Verify with the isolated HR-policy, request-content-operation, Feishu restricted-access/delivery, session-access and protected-source tests. Coordinate business-schema migration and seed validation before enabling registry configuration; preserve exact automation grants, alert receipts and independent work. Rollback configuration must point to a previously validated policy, never an empty allowlist or permissive fallback.
