群消息分流实验 · 2026-10-10 核对

及时接住新消息，分别承担回复责任

研究还在进行时，补充条件和催问可以进入正在运行的执行。系统不再要求它们等上一轮结束，但仍为每条消息保存作者、工作去向和回复位置。

这个实验解决两种等待：后来的消息被前一轮长任务挡住；主线为了选择工作话题，先把业务问题研究了一遍。做法是让主线尽快确定去向，把深入工作交给工作话题，并允许状态答复提前发送。

适用范围：已授权的单群分流试点中新接纳的主线输入。既有工作话题继续在原话题处理；不扩大到其他群或全部会话。实现已核，本实例已加载包含该改动的版本；真实群聊的响应时延和分流准确率仍待测量。

为什么原来会慢

接收、执行和发送本来就由不同程序推进，但分流主线仍按整轮串行：第一条没有结束，后来的消息便不能进入模型上下文。第一轮又提前调查设备和资料，补充、催问因此一起等待。

当时禁用主线追加输入，是为了保护逐条分流和回复：旧结算会让同一次执行中的消息共享最终结果。第一条转到工作话题、关闭主线正文后，后来的催问可能也失去自己的回答。新版同时修改输入接续和结果结算，分别保存每条消息的处理决定。

环节原方案的问题本次机制
新消息进入执行等前一轮结束，补充和催问也排队。兼容输入可 steer，即追加进活跃执行；不固定延时收集消息。
主线选择去向为了分流先做业务研究，交接太晚。只核作者、授权、已有话题和当前状态；深入核查交给工作话题。
回复责任共享一轮最终结果，难以同时满足转交和当场答复。每条输入分别选择移交、本地答复或明确无需正文；兼容补充可显式合并。
催问和接收反馈催问也等调查完成；反馈受附件准备拖延。依据已保存状态提前答复；表情反馈不等待完整附件、背景和正文准备。

2026-10-09 的一个三消息案例中，接收均在 0.7 秒内；第一轮运行约 4 分 22.6 秒，后两条从接纳到启动约等了 4 分 30.6 秒和 5 分 42.9 秒。这两个等候数包含启动时间，不等于 steer 后实测节省的时间。工具批次之间的耗时也不能全部归因为模型思考。来源与测量边界。

整体流程：接续执行，逐条决定去向

Session 是保留上下文的工作会话，Run 是一次实际运行，Request 是一条输入的处理记录。多条 Request 可以进入同一个 Run，但不会因此变成同一项工作。

steer 消除的是“必须等前一轮结束”的依赖。模型仍要到自己的输入读取时机才看到消息；上下文准备、附件处理、工具执行和网络也可能耗时。保留这些必要等待，不承诺所有消息即时回答。

实现入口、兼容条件与逐条结算

canForwardNativeRequest 检查原生运行和输入是否兼容。两条试点输入都须使用协议 2；执行工具、模型、思考档位一致，并通过新线程、取消中、内部操作、复核和文档绑定等现有边界。旧轮次继续沿接纳时的契约，不把旧请求强行转成新协议。

work route 为选择的输入保存工作话题移交；work reply 为指定输入保存答复并立即建立持久投递。两种处理互斥。合并回答须明确列出覆盖的输入，正文发送到选定首条输入的原地址，其他输入保留被该答复覆盖的记录；不向所有消息重复发送同文。

追加输入没有移交或独立答复时，结算明确显示尚未处理，不复制第一条的最终正文。根输入未移交且未提前答复，仍可正常给出最终答复。已提交的答复计划和投递记录支持中断恢复，重复请求必须保持原正文、输入集合与目的地。

不同消息，怎样处理

以下是按当前机制编写的情境示例，不是新增的真实运行样本。判断依据是消息内容、作者、原话题和已保存的工作状态；不能只按“紧接着到达”就合并。

1．新的独立事项

例如已有机械臂研究进行中，又提出“查一下录音按钮的反馈”。这属于另一项工作，可以共享主线执行，工作去向和回答仍分别保存。

核对作者、任务与授权
→
检查是否已有对应工作
→
在本群新建或接续对应话题
→
接纳确认后，结果在工作话题回答

原消息保留接收反馈。重复提交复用已预留的目的地；工作话题创建与首条飞书消息实际送达分别确认。

2．同一事项的补充

例如“还要考虑成本”“用刚才那张图”。先确认它补的是哪个事项，把条件和附件接到原工作，不为每条补充另建任务。

定位被补充的事项
→
接续原工作话题
→
工作端继续执行或接收原生追加
→
在原工作中采用条件并给出结果

相容的连续补充可以一次明确移交；各条仍有自己的作者和回执。含糊的“这个”若会改变任务归属，先问清指代，不猜着转交。

3．催问、状态查询或插入短问题

例如“现在做到哪儿了？”主线先查已保存的接收、排队、运行、移交或投递状态，回答当前能确认的事实。需要调查原因时，调查继续在工作话题推进。

4．纠正条件或要求停止

例如“先别下单，只做方案”“停止刚才那项研究”。必须定位受影响的工作，保留原作者和权限边界，把最新条件接续到该事项。

纠正原事项接收新条件工作端调整后续行为，重查受影响的结论和验收；已执行动作另说明。
停止原事项落实停止并核状态明确对象后走该工作的控制路径，区分要求已接收与执行已停止。

在主线 steer 一条“停止”，不自动证明另一个工作话题已停止。明确的停止控件使用原有取消机制；自然语言仍由 Harness 理解和处理。停止正在执行的工具、恢复已发生的外部动作各有自己的限制。

5．信息会影响另一个已有话题

补充原事项与影响另一项工作是两种情况。跨话题复核要先准备具体草稿，列明目标、内容、影响和返回范围，让人确认这一份同步。

读相关记录，形成同步草稿
→
等待人确认具体同步范围
→
目标话题展示已批准信息并复核
→
复核结果回到来源话题

未确认时只保存草稿。同步限同一试点群；不搬移可见历史、不扩大群权限，不自动取消或替换目标工作。目标若已变化或不可用，按现有校验处理，不能把提交当成采纳。

6．已读、致谢或无需正文的交流

Harness 可以记录无需正文的具体理由，保留适合语境的结果表情。需要工作话题答复时，成功移交后原消息可用“收到”Get 表达接收。

判断无需正文或正文将在工作话题继续
→
保存处理决定
→
投递合适的表情并核回执

表情库有 50 个内置选项，现有轻量判断可选其中 40 个情境表情。Get 表示收到或接下，不表示任务完成；移交成功由目标接纳记录证明，表情自身不证明它。

三条连续消息，如何共用执行又分别处理

假设甲先发研究需求，随后补充条件，乙又催问。这是工作分配示意，不表示实际秒数或客户端送达顺序。

每条追加输入需要明确处理。主线可以在一轮内安排多项工作，但不会自动把所有输入广播给每个工作话题，也不会让多个执行同时改写同一份会话状态。

异常与重试：从缺失的环节恢复

情况系统保留的依据恢复方式与边界
当前运行不能接受追加输入兼容性与原生回执。明确未进入活跃执行时沿正常队列处理；传输结果不确定时先查回执，不能当作新任务重复执行。
目标话题已归档或不属于本群目标身份、可用状态和群绑定。阻止移交，说明原因；重新确认有效去向，不静默搬到其他群。
目标接纳失败或回执丢失固定输入身份、已预留话题和目标请求。按同一身份查询或重试。未接纳时恢复原消息报告失败的能力；不能先宣称成功。
某条追加消息未处理没有该条移交或独立答复记录。结算显示处理未完成；不拿另一条的最终结果充当它的答复。
服务重启、合并答复中断已保存的答复计划、输入集合和投递记录。恢复原答复；保持正文、地址和覆盖集合不变，避免重复正文。
已生成正文，外部送达不确定原正文、出站状态和提供方回执。查原话题或回执，确认缺失后补发原投递；不重新做一遍研究、下单或其他工具动作。

怎样判断实验有效

首先确认每条消息归对事项、回对位置、没有漏接或重复工作，再比较速度。隔离回放能验证传输和记录契约；真实模型是否及时采用补充、把主线调查控制住，仍要用自然消息检验。

维度观察什么当前证据边界
追加是否及时首轮仍在运行时，后续输入能否进入同一次执行。已有隔离回放；不能据此推导线上平均时延。
归属和回复正确补充接原工作；独立事项分开；不同作者地址正确；催问有答复。已验证程序契约；自然群聊的语义准确率仍待测。
人感到快不快接收到反馈、目标接纳、首个有用答复的时间分别测量。需包括准备、启动和上游等待，记录 p50、p95 与最差案例；不能只测模型生成。
恢复和副作用重启、重试、未知回执、目的地变化、停止纠正时是否重复或越界。已有隔离测试；线上每次送达和业务结果仍需自己的证据。

仍待验证：实际能快多少、复杂连续讨论的错分率，以及哪些准备步骤继续占用时间。本次机制没有增加独立分流模型，没有调整思考档位；后续比较模型或档位须用相同样例，同时衡量速度和归属准确性。
