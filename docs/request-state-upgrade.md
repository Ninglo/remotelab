# 旧实例升级：Request 状态格式变更（2026-09-07）

**这是一次不兼容升级，需要安排停机转换。已有旧运行记录的实例不能直接更新代码后重启。** 新版本会拒绝读取旧格式；反复重启不会自动迁移。已转换到 schema 1 的实例不需要重复转换。

可将下面这段交给负责目标机器的 AI：

```text
请按 docs/request-state-upgrade.md 升级这个 RemoteLab 实例。
目标实例：[名称或地址]；可接受的维护时间：[时间]。
正在运行的任务默认等它们结束；不要擅自中断或重发旧消息。
先核对实际服务、代码版本、数据目录和恢复权限，在副本上验证转换与回滚。
如果还有必须由我提供的信息，请一次问全。其余工作完成后，报告迁移数量、
中断或未投递的任务、真实收发验证结果，以及备份位置。
```

## 影响是什么

- 变更从 `12213e27` 引入。原来的运行记录和发送记录转换为 `requests/` 下的 Request / Delivery，完成标记为 `requests/schema.json` 中的 `version: 1`。
- 会话、历史、附件和运行记录应保留。**旧格式的运行中任务不能靠这次转换无缝续跑**；默认等待结束。明确允许中断的任务，必须先停止实际进程，再将记录转换为失败，后续是否继续另行处理。
- 历史普通回复没有可靠的发送记录，转换器不会推断它们应该重发；旧的“发送中”记录转为 `unknown`，需核对真实收件情况。历史邮件、日历等完成后动作也需要单独核对。
- 本次停机转换与日后的普通重启不同。普通重启恢复需要相容的状态格式，以及能保住运行进程的服务配置。

## 升级顺序

1. **确认范围和恢复入口。** 读取服务实际使用的源码、用户、环境变量和数据目录，列出所有 connector、定时任务及单独配置的存储目录。共享一份源码的多个实例分别检查；切换共享代码会影响其他实例的下次启动。准备目标服务停止后仍能使用的 SSH / 终端或维护进程，核实管理服务的权限，把记录放在该入口可读取的位置。
2. **先在完整副本上试转，再停生产。** 保留旧代码提交、依赖、服务 unit/drop-in 和完整数据备份；外置 connector 存储、附件及软链接目标也包括在内。在一致副本上运行转换器，核对 `(sessionId, requestId)` 和 `(sessionId, responseId)` 冲突、历史读取和回滚启动。副本验证不得启动真实消息消费者、定时任务或外部发送。通过后再安排实际停机，重新取得最终快照并转换，不能把早先试转的副本直接覆盖回去。
3. **停止所有写入。** 暂停新输入和定时工作，等待已有任务结束，再停止 connector 和控制服务。检查 detached runner / 工具进程是否还在写入；仅停止控制服务不代表写入已停止。明确获准中断时才停止对应任务，并保留任务清单。
4. **转换到新的暂存目录。** 使用下方命令，检查退出码、`conversion-report.json` 和 schema 标记。核对全部运行 ID、状态变化、会话历史、附件、排队输入与发送记录。失败时保留输出用于排查，从原备份重新生成另一个新目录，不能补写 schema 标记强行启动。
5. **补齐 connector 状态。** 按每个机器人的实际存储目录，核对 `events.jsonl`、`handled-messages.json`、Inbox 和发送回执。旧 handled 记录必须导入新 Inbox 的去重状态；只复制旧文件不够。对没有处理回执的入站消息、没有发送证据的回复分别列出处理结果。**仓库转换器目前不自动完成这一步，也不自动解决重复 ID；这些项目未核对完不能切换。**
6. **切换并验收整个实例。** 所有写入保持停止时切换已验证的数据目录、代码及服务配置；控制服务就绪后再启动 connector 和定时工作。核对登录、旧历史和附件读取，并从实际使用的飞书聊天验证接收、文字和文件回发。再让任务运行中重启 connector / 控制服务，确认任务继续、结果回到原线程且已确认的部分不重复发送；补测 connector 停机期间任务完成、启动后自动补发。记录请求、运行和飞书消息 ID。首个实例通过后才继续其他实例。

转换命令由负责升级的 AI 在停写副本上执行：

```sh
node scripts/convert-request-state.mjs --source <stopped-config> --output <new-staging-directory>
```

`--interrupt-unfinished` 只把未完成记录记为中断，**不会停止进程**。不要为了让脚本通过而直接添加这个参数。重复身份应在副本中逐条对账，保留旧身份与新映射记录；不要删除冲突的历史或批量随机改 ID。

本次升级所用版本需包含后续修复 `2f19c066`（飞书 SDK HTTP 方法）、`27bcf1a4`（HTTP 接收时保留回复目标）和 `3ab7e562`（重启保住执行进程）；只看到 schema 1 不代表修复已加载。Linux 还需检查**实际安装的** unit/drop-in：适用的 owner 服务使用 `KillMode=process`，配置的 `REMOTELAB_RUNNER_SYSTEMD_SCOPE` 对应管理器确实可用；更新源码不会自动更新旧 unit。其他进程管理器也需验证同样的进程存活条件。

## 失败和回滚

- 转换或检查失败，停止切换，保留原备份和失败副本。回滚要同时还原匹配的**代码、依赖、服务配置和数据**；仅退 Git 提交不够。
- 新版本已经接收消息或执行任务后，先保留新增状态并对账，再决定恢复哪份数据；直接盖回旧备份会丢掉切换后的工作，也可能重做外部操作。
- 回滚后验证实际版本、HTTP / 历史读取和 connector 状态；真实回发未验收就明确注明。`systemctl is-active`、端口打开、schema 文件存在都不能单独证明恢复成功。
- 恢复检查失败就报告“回滚失败，服务尚未恢复”，保留独立入口继续修复。不要发送“已恢复”的固定成功通知。需要外部通知时，应使用已获授权且验证可用的通道。

## 这次操作的结论

离线转换、保留原数据和明确处置运行中任务，这个方向正确；首次上线没有充分验证真实旧数据和回滚，造成了超出计划的停机，后来又发现飞书 SDK、回复目标和进程管理的问题。**转换完成不等于升级验收完成。** 具体数量、失败证据和验证边界见[本次事故记录](../notes/archive/2026-09-07-request-state-upgrade-incident.md)。
