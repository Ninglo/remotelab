消息接入、异步执行与用户输出 · 阅读版

一条消息，怎样变成工作和交付？

先可靠收录，再把工作交给模型；模型推进任务，输出程序把开场、卡片和结果送回用户。

关键是区分两次交接：写进 Session 历史，还不等于启动模型；提交可执行 Request，才进入运行调度。Jev 在部分入口参与快判，实际任务由所选 Harness 理解、执行和验收。

· 源码与现有配置快照；现场状态不会自动更新

现在不能说整条飞书体验已经验收通过。

上一轮修复已有回归与部署证据。新的真实复杂任务收发仍待验证；即时表情前置、跨输出 Worker 的到达顺序、提问分级与打断处理还有明确缺口。下面先解释现在怎么跑，再单独标出目标怎么改。

读法：先走 01 的一个场景，再看 02–04 的交接和等待；只关心使用时，可直接跳到 06–08。技术细节和源码折叠在对应位置。图里的时间表示先后，不承诺秒数。

01 / 顺着时间走一条飞书消息的一生

默认选中实际 Jev 试验路径。切换入口后，时序图、步骤说明和等待条件一起变化；目标方案是独立选项，不混进现状。

同一消息的接入处理有先后依赖，但后面的模型与投递会并行推进。飞书表面可能稍后追上 Session 里的最新事实；图里的写入顺序不是客户端到达顺序保证。

02 / 交接点与职责“交给 Session”有两种含义

Session 是持久工作间，Request 是一条被接纳的输入，Run 才是一次实际执行。它们不是三个模型，也不必一一对应。

交接 A · 只收录

Connector → Session 观察历史

消息、来源和近期上下文进入 observations。返回 sessionId、eventSeq、recent。此处不启动 Run。Jev 接下来可以据此快判。

交接 B · 可以执行

Connector → Request 接纳层

提交正文、附件、执行设置和固定的回复位置。保存 Request 后启动、续接或排队。返回请求 / 运行身份；调用方不等最终答案。

Jev 建议复杂工作时，Connector 可以切到工作话题 Session；否则常见做法是续接原群 Session。话题绑定采用实际飞书回执，不能把“准备了话题目标”说成“用户已看到话题”。

展开每个对象留下什么
对象谁维护留下的事实不能据此推出什么
inboxConnector来源事件、去重键、处理 / 重试状态不能推出模型已启动
SessionRemoteLab规范化历史、来源绑定、原生继续标识不能推出每条收录消息都有 Run
Request接纳与调度层稳定 requestId、输入快照、回复位置、接纳回执不能推出新增信息已被模型采用

delivery / 卡片回执各输出程序发送状态、messageId / reactionId、版本、提供方回执API 成功不等于真人已读；单个分片成功不等于全部交付

03 / 等什么，不等什么“用了 async”不代表用户不用等

JavaScript 的 async / await 是写法。这里要看业务依赖：Jev 调用虽是异步网络调用，Connector 仍然等它返回才提交执行请求；Run 和输出投递则可以在接纳后独立继续。

前置串行 · 当前 Jev 试验路径
inbox 落盘→Session 观察收录→等 Jev→执行请求接纳→排表情

每一步依赖前一步的事实。即时收到确认尚未从这条链路里移出。

接纳之后 · 独立推进

执行：Harness → 工具 → 发现 / 验收 → 最终结果

文本与表情：事件 → source-delivery outbox → Connector → 飞书回执

任务卡：workboard / progress → 个人试验 Worker → create / patch 原卡

后置：运行结束 → 条件触发摘要整理 / 记忆归集

模型不等卡片 Worker 的飞书回执才继续干活；最终答复不等标题和记忆整理。

文本 outbox 与卡片 Worker 是两条独立程序，所以现在只能说开场事件先形成，不能承诺开场一定先于卡片在飞书客户端出现。如果产品要求严格先后，需要补持久的投递依赖。

断线、重启和发送失败怎么接住

接纳和运行身份保存在耐久记录中；执行脱离浏览器连接。重启按原身份恢复观察和请求，不靠再次发一遍用户消息。

发送失败沿既有结果与分片身份重试投递。发送状态不确定时应先核对回执 / 读回；卡片首次 create 的结果未知时，不能无条件再创建第二张。

网页 WS 是“有变化了”的通知，重连后从 HTTP / 持久历史重新读事实，不能把 WS 消息当唯一完成证据。

04 / 判断与发送分别是谁Jev 不只选表情，也不执行任务

Jev 返回的是判断结果。固定程序把结果变成路由或投递请求；真正的调查、工具操作、任务拆分和结果写作交给当前 Harness。

位置Jev 做什么当前是否等待后续由谁承接
飞书 Jev 试验入口建议参与方式、表情、短答 / 复杂工作位置是。观察收录之后、执行请求提交之前 awaitConnector 保存决定、准备工作位置，提交 Request；Harness 决定实际是否回复
Auto 运行档位只在选择 Auto 时做运行档位路由条件发生，在 Request 接纳前解析调度器把已选定的执行快照交给原生运行器；固定档位不用这次路由
是否需要任务卡旧 Jev 清单 gate 已退出入口没有额外清单模型调用可建卡、已启用的工作 Session 中由 Harness 按实际工作量决定
飞书表情 / 文本发送不直接发送Jev 返回后才可能排入投递Connector 调提供方 API；返回真实 reactionId / messageId
后置标题与摘要另有 Session 状态分类器，不是群 Jev 快判不阻塞最终答复独立后台流程整理元数据；不是任务验收人
Jev 的静默建议目前不阻止已观察消息进模型。

当前代码采用临时 fail-open：保留表情和位置建议，把已观察消息交给 Session 模型自行判断答复。但 groupFeed 旁听 Session 被排除在任务卡范围外；位置判断仍会间接影响有没有新卡。不能把“清单 gate 移除”理解成所有群消息都能建卡。

展开判断输出与成本边界

保存的决定包含 participation、emojiType、workMode 和理由。Jev 上下文是有边界的近期消息与可用记忆摘录，不是整个公司的全部对话。

群快判、Auto 路由、主 Harness 执行是不同调用。飞书 API 显示一个表情，并不意味着只发生了一次 API 或没有模型成本。当前没有用新的外部事件机制自动替代这些职责。

05 / 分开看入口试验入口、常规入口与飞书

入口谁先接收哪些判断在前面输出怎么回去
网页 · 个人试验当前 Session 的 HTTP 接纳层结构校验；Auto 仅条件启用。没有飞书群快判网页读取规范化历史和个人启用的 workboard 投影
网页 · 常规同一 Session / Request 底座同一运行规则，任务卡是否可用看部署和个人开关普通会话投影；不能由“常规端口”推断已升级了任务卡
飞书 · Jev 群试验Connector 的耐久 inbox先观察收录，再等 Jev，提交工作后排表情文本 outbox + 独立卡片 Worker；复杂工作可开话题
飞书 · 非 Jev 配置同一 Connector inbox按访问、@、回复模式和 quickReactions 分支处理原消息 / 原话题；符合试验范围才有卡片 Worker

“没有 @ 也能唤醒”是已配置群的能力，不代表任意群、任意机器人消息都触发工作。现有群旁听与话题工作 Session 也不是一回事。

话题内后续消息沿已绑定 Session 续接。群主线发起复杂工作时，Connector 保存原消息回复目标；首条 Bot 回复创建或取得话题，再记下绑定，后续回同一位置。

展开回复位置为什么不会跟着新消息跑偏

每条 Request 保存自己的 sourceDelivery，包含 Connector 路由和该输入的回复目的地。即使后来 Session 又接到另一条消息，延迟结果仍按原 Request 的位置交付。

Session 绑定、inbox 去重、Request 去重、文本投递身份与任务卡 messageId 分别维护。它们互相衔接，但不能只凭 Session 存在就判定群里已经回过话。

06 / 用户看到的过程一次开场，一张推进卡，一个本轮结果

快速任务直接给完整结果。较长且可建卡的任务，先让用户知道具体怎样着手，再用同一张卡跟进工作。需要用户回答的问题单独出现。

三种状态各有维护者

Run 状态：调度器 / 原生运行器记录接受、运行、停止或结束。

任务状态：Harness 按验收证据记录进行中、部分完成、等待、失败或完成。

交付状态：输出程序按真实回执记录待发送、部分送达、失败或全部送达。

完全可能同时出现：Run 已结束 · 任务部分完成 · 本轮最终答复已送达。也可能任务已经验收完成，但最终附件尚未送达；此时恢复投递，不重复执行任务。

07 / 运行中又收到一条消息停止、插问、补充和回答不能混为一谈

底座支持原生追加输入与停止，但目前并没有把所有自然语言反馈可靠分成独立业务事件。尤其是正在等选择题时，新文字可能被当作题目答案。这一点必须单独测试。

用户动作当前机制目标与缺口

超时选择是系统回退，不是用户回复，更不是授权。现有统一五分钟策略与目标的“可选 / 必要输入 / 授权”分级不等价；目标的持久待答、问题版本和独立交互卡还需要实现。

为什么“已接纳补充”不等于“补充已采用”

HTTP 接纳证明输入被可靠记录。原生输入回执证明它送到当前执行。模型随后解释“我已采用这条信息，因此把 A 改为 B”，并重新验证受影响结果，才说明它进入了实际方案。

原生追加输入不能自动保证插问后继续原任务，也不能替代验收。Harness 需要说明原任务的去向，并用原 taskId 更新已有卡。

08 / 可以去测，但不能先宣布都通过把体验验收落到实际收发

你可以现在测试。建议先测“复杂任务无 @”和“运行中插问”；有选择题时，再分别测试停止按钮与普通文字。验收看真人入口、真实投递回执与实际卡片更新，不用静态图或 CI 代替。

场景实际看什么当前边界

这轮已经改的，与还要改的

  • 已改：移除 Jev 清单 gate；新工作由已启用的执行 Harness 判断卡片需求；有用开场合入入口；有卡时进度更新原卡；最终答复与任务完成分开。
  • 仍待：收到表情从可靠接收点立即触发；两条 Worker 保证客户端开场与首卡顺序；问题等级与持久待答；自由文本停止、插问与问题答案的区分；旁听 Session 中工作变长时的任务卡接续规则。
  • 还没拿到：部署后新的真人复杂任务，从消息接入、首卡、原卡进度到最终答复的完整飞书验收证据。

本页这次交付的是说明网站与事实核对。它不会把上面待改能力自动部署，也不会改变之前尚未通过的飞书端到端验收状态。
