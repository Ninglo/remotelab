RemoteLab 文档

从一条消息开始

你发来一句“帮我查一下”。RemoteLab先接住这条消息，确认它应该进入哪里，再把任务和必要的上下文交给Agent。Agent在真实机器上读资料、调用工具，把结果送回你发起工作的地方。

接收到消息、模型开始工作、任务通过验收、结果真正送达，是四件事。下面沿同一条消息往下走：先看它能不能进入工作，再看开工时带了什么、执行中怎样接住你的补充，最后看结果和记忆怎样留下来。

01　先接住消息，保留它从哪里来

网页消息已经选定一个Session。飞书消息要先经过Connector——负责连接外部聊天服务的程序。它把原事件写进耐久inbox，按原消息身份去重，再确定对应群主线、话题或工作Session。其他连接器沿自己的接入协议处理，不能套用飞书的群规则。

消息进入任务时，正文和附件之外还带两组信息：sourceContext说明这条输入来自哪里；sourceDelivery说明这一轮结果应该送到哪里。两者随请求保存。正在执行时又来一条消息，要保留新消息自己的来源和目的地。

中文、英文或混合语言仍是任务正文。这条主流程没有按语言决定“要不要回”的统一门槛；来源规则判断接入，Harness理解内容并尽量用对方的语言回复。语音、图片、文件能否读到，取决于该来源的实际解析和附件准备结果；看到文字预览不等于原文件已经保存。

来源字段、身份与收录证据

连接器服务凭据证明程序可以提交，不证明消息作者是谁。Person须由本轮验证的Identity关联；未知作者保持未知。群中被提及的人、Session创建者和机器用户名都不能替代当前作者。

按原消息标识查连接器inbox及来源索引，再用requestId对到Request、runId对到执行。平台上下文把来源值作为数据投影；完整快照沿原source-context接口按请求查，不靠页面摘要补猜。

02　先分清接入判断和回复判断

网页里的明确请求直接进入接纳流程。群消息先要回答另一个问题：这条讨论应该交给这个Bot吗？飞书Connector按发送者、静音状态、群配置、真实@和已有话题绑定判断。自己发出的消息被抑制；其他Bot交接需要明确@；私聊、人类群讨论和已经加入的话题各有不同规则。

通过接入后，群内仍可能只是同事之间在说话。来源的参与机制给出建议；接纳并交给Harness后，它才结合最新消息、近期讨论和用户要求决定实际回复。接入成功并不要求每条消息都发一段文字。

输入或模式怎么判断与承接等待与输出
网页直接请求结构与身份检查后接纳；Harness理解任务。没有飞书群参与快判。HTTP返回接纳回执，网页继续读取运行事件。
飞书常规接入固定来源策略先过滤。启用旧Quick participation时，Jev快判可与收到表情并行；已接纳的正式工作不以该快判为启动门槛。Quick路径可等收到表情回执，不等Jev结论；其他处理表情可异步发送。
飞书Jev观察路径先保存Session观察消息，再等待有限上下文的Jev判断；它建议表情、短答或复杂工作的位置。当前临时fail-open仍把获准参与的观察消息交给Harness决定回复。等待Jev和决定保存，再提交执行。silent或只回表情的建议本身不再保证没有Run。
暂停／监听参与控制已启用时，暂停路径只观察；监听路径默认不运行、不发表情、不准备任务附件，除非当前消息明确邀请并通过控制判断。当前实现中暂停检查在快判前，监听授权检查在快判后；不能用fail-open绕过这两种状态。
固定查询／控制命令例如无正文的/help，由命令程序处理，不当作普通工作请求。固定答复可直接走投递，没有这次普通Harness工作。
已有定时／事件任务Trigger携带已登记的任务、来源与执行身份，不经过飞书人类群消息的同一套接入快判。到点只是触发机会。Agent先核对目标与实际进展，再决定行动、调整或保持安静。

“自动回复”描述系统怎样承接输入；“主动回复”描述Agent在已有授权和当下状态下是否值得介入；运行设置中的“Auto”则只选择执行档位。它们是不同的决定。Jev的建议不产生新的业务授权，明确的暂停、禁发和任务范围继续有效。

Jev当前做什么；哪些配置改变这一分支

群设置由responseMode、participationMode、quickReactions、jevReactions、groupFeed及参与控制组合而成；实现校验部分组合的前提条件。Jev读取有限近期窗口，可按配置加入有日期的项目报告摘录，不是检索所有聊天历史。

新观察路径中的顺序是：持久观察 → 参与控制 → Jev与保存决定 → 监听授权复查 → 提交工作 → 条件表情入队。临时fail-open位于最后两步前，不能据旧图推断silent零模型成本。旧Quick快判、群观察快判、Auto档位选择是不同调用。群分支的Jev用量也不能从普通Run账本完整推导。

本节按源码解释分支，未把历史“2个旧群、1个试验群”的快照更新成当前覆盖量。逐群是否启用须在对应实例安全读回。

03　接纳一项工作，确定这一轮怎么运行

Session是持续保留记录的工作间；Request是这一次输入的耐久记录；Run是实际执行。一个Session可以承接多轮工作，运行中追加的多条Request也可能被同一Run采用。

接纳层检查输入、去重，并固定这一轮的运行设置和回复目的地。重复提交相同请求身份时，应读原回执，而不是再做一遍。选择Auto档位时，接纳前可能多一次路由判断；明确设置的档位沿保存的设置走。

接下来有三种结果：空闲时准备并启动新Run；同一原生Harness正在工作且输入兼容时，把补充交给它；不适合加入当前执行的输入保留在队列里。工作中切换不兼容的模型等设置会被拒绝。队列位置、请求已接纳、原生输入已接受都不是任务完成。

接纳回执、追加输入与中断恢复

POST /api/sessions/:id/messages返回requestId、运行／响应地址及queued、duplicate等状态。原生追加输入保留独立request/response身份，通过nativeDispatchRunId关联实际执行。回执丢失时先查原身份，不能制造新Run来猜一次。

Codex、Claude、Pi等使用各自原生输入协议，何时把补充用于模型推理或工具由Harness决定。网页断开不终止脱离前台运行的sidecar；控制服务恢复和原生进程自身崩溃是不同故障。详细协议与恢复边界在追加输入和仓库原生输入文档。

05　开始做事，也继续接住你的补充

群输入实际要不要回复，以及怎样理解任务、选择工具、修改文件、判断结果和写答案，交给Harness。RemoteLab启动并观察运行，保存原始输出和规范化事件，把机器能力接到本Session；它不另写一套规划来替换Harness的任务判断。

需要调查的工作先给一个有信息的开场：理解了什么、第一步查什么。明确启用任务卡且范围允许的复杂任务，再由Harness提交目标和可验收的交付项；简单问题直接答。卡片保存结构由程序校验，某项工作是否真的通过验收仍需Harness判断证据。

工作中你说“字体换成得意黑”，这是对当前目标的补充。兼容的原生输入尽快交给正在工作的Harness，它决定何时采用并继续原目标。需要澄清时，通过当前会话提问；无答复不能被记成人的确认。停止、明确取消和另一个不兼容目标也要按真实输入处理，不能把所有新消息都当成替换任务。

执行、按需读取、进度投递会交织。只有查到新事实、出现真实阻塞或形成可用结果时，才值得发进展；工具还在运行不是定时刷屏的理由。

谁决定卡片、问题和任务是否完成

workboard有目标、item、验收条件、revision和证据引用，续作沿用原taskId。它有部署／个人启用与Session范围条件，groupFeed旁听Session不等于工作Session，不能保证都有卡。平台检查证据引用存在，不能仅凭引用的seq替人断定业务成功。

原生问题、停止和追加输入有独立事件与回执。传输已接受不证明模型已经采用，Run结束也不证明所有任务通过验收。原生问题的默认选择是系统默认，不能当成用户同意；涉及批准的更高优先级约束继续有效。

06　让结果真的到达，而不只是留在机器上

Agent产生输出时，平台持续保存事件，网页可从历史和当前运行投影读取。绑定飞书等来源的开场、问题、最终答复和附件，则进入耐久outbox，由Connector调用外部服务并保留回执。任务卡是另一条Worker，读Session快照后创建或更新同一张卡。

因此，模型已经开工时卡片可能还没显示；开场事件先生成，也不保证在飞书客户端必定比卡片先到。两条程序没有统一到达屏障。最终答复与后置记忆整理也不必互相等。

Agent验收的是实际工作：改动是否符合目标、必要检查是否通过、文件能否使用。投递程序验收的是发送：有无真实外部回执、送到哪个位置、附件是否可打开。最终回复要让人知道结果和剩余阻塞；机器里有一个路径、Run显示completed或HTTP接纳成功都不能替代这些检查。

投递去重、未知发送结果与文件交付

同一原生执行采用多条输入时，保持每条输入的reply目标；同一对话保留去重约束，不向同一位置重复发完整结论。提供方发送失败沿原投递身份恢复；结果未知时先查回执或读回，不能无条件再create第二张卡或重发副作用动作。

文件只有需要给用户编辑、导出或分享时才发布到可访问的资产、网页或原业务文档。纯解释在对话中完成即可。修改Git项目沿仓库规定的验证、提交和远端交付；私有本地主账没有远端时，不称为远端交付。

07　工作结束后，留下什么给下一轮用

Session历史和Run结果保留这一次发生了什么。满足条件时，后置流程还会整理标题、摘要或审阅值得留下的候选记忆；这些后台工作有自己的触发、成本和跳过条件。内部维护运行和groupFeed等并不走同一轮后自动写回路径。

本实例现行自动记忆写回仅允许两个候选目标：用户侧reference/inbox.md与平台侧memory/auto-system-memory.md。写入候选不等于成为有效偏好或共同规则。候选要核对作者、原始来源、适用范围和有效状态，再归回原维护位置。

项目事实与参与进度回项目唯一主账；个人称呼和协作偏好回已核Person档案；公司稳定背景回公司档案。项目、人员、公司是并列业务归属；来源、指针、规则、方法和派生日报各做自己的事。来源不清的旧内容留待核，过期或暂停事项不会因为整理而恢复。

下一次工作沿正常入口查这些记录。入口能找到、文件有正文、Agent本轮实际读过，以及它据此正确行动，分别需要证据。记忆章解释续接与读取；时间线解释来源和被替代关系。

后台触发、允许目标与归档边界

scheduleDetachedRunMemoryWriteback先排除内部操作、内部Session和groupFeed；记忆审阅再按环境开关和目标策略运行。writeback-targets.json存在时只启用明确允许项，不能删除它来回到旧默认。新候选附来源信息；旧条目缺的身份与时间仍缺，不能补猜。

共同操作规则经确认后进适用AGENTS.md；可重复方法进原Skill／WORKFLOW；局部话题约定留原任务。日报、网页和总结是派生视图，不复制主账成为第二个事实源。归位前备份和校验，保留旧路径、段落映射与原始历史；不修改原Session事件或Run结果来消掉旧错误。
