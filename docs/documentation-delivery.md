# 说明如何随项目更新

说明正文在仓库原位置维护，网站展示同一份内容。README负责入口与概览，专题文档负责具体用法；历史说明保留自己的日期，源码版本不代替实例部署版本。

## 候选标准操作 v0.1

2026-10-12整理。以下步骤供其他项目试用；后文是RemoteLab已经接通的具体实现。当前有RemoteLab、具身前沿和副屏三个场景的经验，但它们来自同一轮工作，不能据此认定所有项目都适用。维护正文仍在本文件，网站从这里生成，不另建操作台账。

**适用情形：**新增或修改功能、工作流、使用入口、启用条件、实例配置，或者发现说明与实际行为不一致。只讨论方案时可以用它检查缺口；执行修改和发布仍以当次任务授权为准。

给执行者的起始请求可以是：

> 请按项目说明同步的候选标准操作，处理【项目／功能】这次【变化】。先找现有正文、目标实例与用户入口，确认变化影响哪些说明；同步修订原文并沿原发布渠道交付，保留历史、评论和关联。验证实际用法及用户看到的内容，报告尚未完成的部分。已知入口是【链接或路径】，其余信息先从项目现有记录查找。

执行前在原任务中记清五项：对应功能及变化、正文来源、适用实例与条件、用户入口、实施者及长期维护角色。未知的关键项先核实，不凭机器名推断负责人。记录复用原功能目录、项目和部署记录，不复制成另一套主账。

### 每次变化走五步

1. **找对原件。** 读取现行正文、相关实现及实例状态，沿正常入口确认用户目前看到什么。区分通用用法、实例差异和历史快照，找出旧新指引冲突。
2. **判定影响。** 列出受影响的功能和段落；新增功能没有对应说明时明确补关联。没有影响也写具体原因。文件变动检查帮助找遗漏，实际使用方式决定要不要改正文；配置变化和服务外部依赖变化同样要判断，不能只等Git提交。
3. **在原处修订。** 实施者把功能变化与对应说明放在同一次交付中。README负责入口，专题文档讲完整用法，实例记录保存差异；修正失效段落，保留历史、评论和原对象ID。已有生成机制时只改源文件，生成页不另维护正文。
4. **沿原渠道发布。** 复用项目的构建或发布事件，记录正文版本及适用范围。动态状态从业务源读取；只能展示快照时标明采集时间。自动发布只覆盖已接入的正文和渠道，其他内容明确由谁、在什么变化发生时更新。
5. **从用户入口验收。** 核对真实用法与正文、正文与页面是否一致，检查链接、图片、登录权限，以及电脑和手机阅读。保存来源版本、发布回执与实际运行版本，分别说明已验证到哪一层。没有核实的内容保留“待复核”，不能只换日期或版本号宣称完成。

完成时在原任务留一句可核对的记录：**这次改了什么；对应正文与用户入口；适用实例／版本；如何验证；仍缺什么。** 实施者负责本次同步，项目原维护角色负责长期内容；角色尚不明确时如实写明，不擅自给某个人分配任务。

### 三种接入方式

| 情形 | 沿用什么 | 需要注意什么 |
| --- | --- | --- |
| RemoteLab这类Git项目 | 功能与文档关联检查、提交／合并事件、原网站生成与发布 | 只接入目标源码目录及实例；提交成功、网站发布和服务部署分别核对 |
| 具身前沿这类非Git内容项目 | 原内容ID、版本历史、构建流程和发布入口 | 修改原使用指南后随构建刷新；没有接通提交钩子，不宣称已获得Git项目同样的自动检查 |
| 副屏这类设备功能 | 同仓使用说明、原设置入口和部署维护记录 | 软件页面与设备固件／代理可能不同步；下载或USB回执不能代替现场观察 |

### 失败、例外与后续标准化

发布失败时保留现行站点和失败原因，修复后复用原发布器重试；若需要回退，沿原备份校验和恢复。其他项目首次采用时，要实际核对它的失败保护，不能假定已有同样能力。绕过事件入口、旧新来源冲突、权限变化及未登记功能，都应回到对应步骤补齐。需要人判断的研究综述、设计原因和设备外观仍由人或执行者核验；不靠AI重写全文或新增全库轮询代替验证。

下次在不同项目或由不同实施者复用时，把遇到的遗漏、误报、失败恢复和额外维护成本记在原工作结果，并修订本节。确认这些步骤能稳定完成、例外可处理，再按项目原流程将其确认为正式标准；在此之前保留“候选”状态，不自动扩展到所有项目。

## 修改功能时

提交前运行 `node scripts/check-documentation-impact.mjs --staged`。检查器复用功能目录中的源码与文档关联，列出本次变化涉及的说明，覆盖服务、前端、自动化、本地助手和运行脚本。改使用方式、启用条件或接口时，同一提交更新对应正文；修正旧段落，不只在末尾追加一条更新记录。

确实不影响说明的修复可在提交信息写 `Docs-Impact: none — 具体原因`；本地commit-msg检查会读取这个理由。它是可审阅声明，不是机器证明内容正确。测试、纯文档及样式文件变化无需强行改README；新增未登记实现会提示补功能目录或README入口。新功能仍应补入原功能清单。

## 网站生成与同步

`node scripts/documentation-site.mjs build --out /tmp/remotelab-guide` 从原目录组装网站，重新生成功能与产出页，并把目录中登记的Markdown正文生成可阅读页面。正文引用的本地图片随站点打包并记录哈希。文件清单附源码版本与输入哈希；原件链接保留，生成页不另写正文。

GitHub Actions CI已退役。文档影响在本地提交前检查；需要验证完整站点时运行上述build命令。实例维护者在已授权的源码目录执行 `node scripts/documentation-site.mjs install-hooks`，登记该实例原静态发布目录；已有Git钩子不会被覆盖。之后本仓库的commit和merge事件触发同一发布器，发布到原slug；无需新增定时任务。

自动出版使用已提交快照，不读取其他人的未提交编辑；仅当文档输入改变时重新生成。说明站明确使用 `--access public`，不继承内部业务站的员工登录默认值。发布前扫描公开产物并读回文件哈希，失败保留旧站及本地失败回执，在Git命令输出报错。提交本身不因后置出版失败而回滚。直接fetch、reset、手工改文件及绕过钩子的操作不会触发发布；这类部署完成后运行 `node scripts/documentation-site.mjs publish` 补齐。新机器也需登记自己的出版目标，不能沿用其他实例的私有配置。

发布回执和备份留在原实例的私有目录；不把运行配置、研究私有材料或个人信息放进公开说明。网站是已发布源码的说明，实际服务仍须分别读取 `/api/build-info` 与对应配置。原架构章的历史样本不会被新网站版本改成“今天已验收”。

## 验收与恢复

代码检查只能定位变化、检查来源和保证生成一致，正文是否准确仍由实施者依据实际行为核验。至少检查对应段落、正常入口、手机阅读与发布内容。说明输入未变的提交不会重复出版。

暂时停止自动出版可将 `.git/remotelab-documentation.json` 的 `enabled` 设为false。失败修复后运行publish重试；旧站保留到新的完整产物通过检查才替换。每次出版保留文档源码、完整站点、输入清单与校验和，可以从原备份恢复，不删除历史评论或原项目记录。
