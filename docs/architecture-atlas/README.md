### 文字怎样组织

读者需要知道工作发生了什么，以及遇到问题时去哪儿查。标题写具体主题，例如“消息记录与请求接纳”“持久状态与读取”。正文把负责的人或程序、动作、原因和结果连起来。术语在首次需要时解释，后续使用同一个名称。句子长短随内容变化，不把每段压成相同结构。

正文供普通读者理解；相关字段、接口、文件、调用关系、数据限额和源码基线放在对应的展开项里。较长实现解释用`details[data-technical]`，标题说明展开后能查什么。会改变判断的当前状态和缺口留在可见正文。普通版和技术版共用内容源。

编辑时参考[Humanizer](https://github.com/blader/humanizer/blob/225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8/SKILL.md)的检查方法：先找模板化段落，再按原意重写，最后对照原文核查。删掉重复总结、无信息的开场、装饰性排比和反复解释文档怎么写的句子。技术说明保持平实，不为了显得自然而添加虚构经历、口语反应或新事实。来源、日期、范围和有效状态保留；引述与真正需要辨析的对照按原意处理。

### 关系和信息流怎样画

工作流程优先用程序框图，跨组件交接用时序图，对象和文件职责用关系图或思维导图。同一组字段仍适合表格。图应帮助读者找关系，不把所有正文都包装成方框。

聊天消息中的流程展示沿用[消息内流程规范](../inline-flow-display.md)：文字先说明结论，需要表达复杂关系时附完整的横向缩略预览，点击后在当前页面放大阅读。展示与交互细节只维护在原规范，本项目保留共同的写作与事实约定。

方框写组件或具体动作，箭头说明输入输出、交接或依赖。执行中反馈、条件分支和后台整理分别画出；同时发生的工作不能因为排版方便画成先后。现状、目标和虚构例子保留文字标记。节点旁的说明继续提供触发条件、异常和来源，图不会替代实现依据。

总入口的消息框图、上下文关系图与对象图由HTML语义结构和CSS构成，文字与图形使用同一组内容，无脚本也能读。各章现有的交互式SVG、时序图和场景切换继续引用原数据。窄屏长图可在自己的容器中滚动，正文不横向溢出。节点可用键盘操作，展开内容或选中状态可辨。

- `配置已核`表示曾读取相应实例配置；`运行记录已核`表示曾读到执行记录；`设计方向`与`待核验`不能作为已上线能力引用。
- 资源快照于 2026-09-29 13:07 中国时间读取。目录大小来自 `du -sB1 -L`，对迁移后的链接取目标目录；模型用量来自最近 7 日 `queryUsageLedger({ days: 7 })` 汇总。静态页不会自动更新这些数值。账本不覆盖连接器单独调用的 Jev 快速判断，也不代表提供商账单。

## 更新方法

1. 在 `situation-data.js` 更新情形和状态层。每个情形都填用户可见结果、决策与执行、读写层、成本、下一次读取、判断边界和源码；`reads`/`writes` 同时驱动条目交叉链接与矩阵，不要只改展示文字。
2. 在 `journey-data.js` 更新单次输入阶段或入口分叉。每个入口都必须覆盖同样七个阶段，每阶段填齐用户端、处理与判断、持久状态、资源、协议、代码入口及横向对照标记；跳过 Run 时明确写出为何跳过及后续交付。阶段编号只是该入口的阅读坐标，不是全系统时序。
3. 在 `experience-data.js` 更新深入场景、飞书规则、资源快照；在 `atlas-data.js` 修改机制节点、跨轮路径和证据状态。节点 ID 应保持稳定，源码锚点要能打开。
4. 核对源码入口是否仍存在、行号是否有效，再更新页面上的源码基线和日期。实际部署版本与实例配置要单独读回。
5. 使用一条真实案例串联 Request、Run、结果投递和外部回执；只有完整证据才能把“待核验”改成“运行已确认”。
6. 发布前检查所有静态资产，不能包含群 ID、会话 ID、凭据、内部 URL、用户原文或其他不适合公开的实例数据。
7. 覆盖同一公开 slug 时，同步更新 `index.html` 的脚本/样式查询版本和 `app.js` 的数据模块查询版本；`situations.css` 管情形与状态层，`reading.css` 管阅读层，`styles.css` 保留基础与参考视图样式。公网缓存会保留旧资产，不能只替换文件。对已打开旧页的用户，提供带新查询版本的入口 URL。

本目录是静态 HTML、CSS 和原生 JavaScript，可以直接由静态站点服务提供。网站的源码入口指向此版基线，后续更新时需一起调整。

## 说明巡检与自动更新的接入办法（拟议，尚未启用）

日度检查版本、相关源码变动、引用符号、目录／锚点和静态资源；周度补充有授权的去标识案例，串联来源、Request、Run、交付与实际读取。相关变更先定位本项目段落，再核源码、实例配置或真实证据；只做必要来源检索，不扫描全部聊天。没有变化只记录版本和范围。

发现矛盾先列待核，不凭自动摘要把“目标”改成“已上线”。历史样本保留日期，已被替代的规则说明原因；正文在原内容源修订。检查记录留受控实例，公开页仅放结构、核对结论及去标识例子。服务版本、源码实现、配置开关、案例成功和组织覆盖分别标记。

要自动执行时先检查既有Trigger／Schedule并复用合适入口，核身份、范围和发布权限。这里没有创建计划任务或第二个采集器。后续改动按本项目既有构建、CI、main、原slug发布、匿名回读和恢复验证流程交付。
