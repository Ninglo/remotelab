# RemoteLab：一条消息如何变成工作和交付

版本：v3 · 2026-10-03。源码快照：`2e300793188aeabddba720df872c3ac4f1c0a5f2`。

阅读入口：[当前流程与交接](index.html)；[目标图与交互演示附录](reference.html)。

主线源码；7696 的现有个人任务卡试验；已启用 Jev / ambient / groupFeed 的飞书群。其他部署实例需要单独核对。

先可靠收录，再提交可执行 Request。写入 Session 观察历史不启动 Run；Jev 在部分入口参与前置快判，实际任务由 Harness 执行和验收。当前飞书新复杂任务完整收发仍待验收。即时表情前置、跨 Worker 到达顺序和问题分级仍待实施。

## 当前流程与独立目标

前置调用按依赖顺序推进；接纳后的模型、投递与后置支路并行，编号供阅读，不构成全局到达顺序保证。

### 飞书 · Jev 试验路径

当前源码与已配置路径。以“群里发一条没有 @ 的复杂问题”为例。这里只描述已配置接入范围内的真人消息；命令、自发机器人消息及访问策略有自己的前置处理。

#### 1. 收到事件并写入 inbox

用户 / 飞书 → Connector；承担者：飞书 Connector + 耐久 inbox；交接方式：sync。

长连接拿到消息后，先把可重放的事件写入本地 inbox。同一来源标识去重；记录成功后唤醒处理器。重启后可恢复尚未处理的输入。

交接：输入：来源消息 ID、内容、发送者、群 / 话题。输出：耐久 inbox 记录。

等待：等待落盘，不等 Jev 或 Harness。此时只是平台可靠收录，尚未启动任务。

可见与证据：本路径目前没有从 inbox 落盘立即触发表情的统一实现。

#### 2. 先写入 Session 观察记录

Connector → Session / Request；承担者：Connector 路由 + Session observations API；交接方式：sync。

检查接入策略，找到已绑定 Session 或创建相应 Session。把本条消息写入观察历史，取回近期消息供快判使用。这里只收录，不创建执行 Run。

交接：输入：sourceMessageId + requestId + text + sourceContext。输出：sessionId + eventSeq + recent。

等待：Connector 等待 observations 回执。Session 已有消息，不等于模型已经接单。

可见与证据：第一次交给 Session：交的是记录和上下文。

#### 3. 等待 Jev 判断并保存决定

Connector → Jev；承担者：Jev 判断；固定程序保存和执行决定；交接方式：sync。

Connector 收集有限的最近上下文，必要时读取已配置的项目记忆，再调用 Jev。它建议表情与工作位置、短答或复杂工作；判断会被保存。

交接：输入：最近消息、是否 @、最新正文、可用记忆摘录。输出：participation / emojiType / workMode / reason。

等待：这一步当前确实 await Jev，是执行请求提交前的串行等待。快判失败有回退路径，但平台错误仍可能阻塞。

可见与证据：当前临时 fail-open：即便 Jev 建议静默或只回表情，也把已观察消息交给 Session 模型决定是否答复。

#### 4. 决定工作位置并提交任务

Connector → Session / Request；承担者：Connector 选路由；Session 接纳可执行请求；交接方式：sync。

Jev 建议 complex 时，Connector 选择话题工作路径，并携带近期群上下文；其他情况通常续接原 Session。准备附件、上下文和本条 sourceDelivery，提交执行请求。

交接：输入：判断结果 + sessionId + 正文 + sourceDelivery。输出：可执行 Request、Run 身份与回复目标。

等待：等待请求接纳，随后独立执行。创建了 Session、准备了话题目标，都不等于已发出一条飞书话题消息。

可见与证据：第二次交给 Session：这次交的是可以执行的工作。话题首条 Bot 回复送出后，才取得真实 threadId 并绑定。

#### 5. 再把表情放进投递队列

Connector → 输出 Worker；承担者：固定程序入 outbox；Connector 调飞书 API；交接方式：async。

若已保存的 Jev 决定有 emojiType，在执行请求提交之后排入 reaction delivery。独立投递器真正发送，保存 reactionId / 回执。Jev 自己不调用飞书发送接口。

交接：输入：原消息位置 + 表情决定。输出：reaction delivery；发送后才有提供方回执。

等待：这里只排队，不等待完整模型答案；表情仍可能晚于模型开工甚至开场。

可见与证据：“表情必须最快确认收到”是目标要求；此路径尚未前置到 inbox 接收点。

#### 6. 启动、续接或排队

Session / Request → Harness / Run；承担者：RemoteLab 调度器 + 原生 Harness；交接方式：async。

空闲时启动脱离前台的 Run。同一原生 Harness 正在运行且输入兼容时，把追加文字送入当前执行；不能加入当前执行的输入按队列处理。切换正在运行的模型等配置会被拒绝。

交接：输入：已接纳 Request 和执行快照。输出：原生输入回执、Run 事件与状态。

等待：浏览器断开或 Connector 结束本次请求不会停止 Run。追加输入回执与模型如何采用输入是两回事。

可见与证据：此时才是模型真正承接执行。Session 是持久工作间，Run 是一次运行。

#### 7. 形成有信息量的开场

Harness / Run → Session / Request；承担者：执行 Harness 写内容；RemoteLab 保存事件；交接方式：sync。

模型说明自己理解到的具体问题、首个待判分叉和要核查什么。开场内容不是固定程序代写的“已创建会话”。快速完整答案可直接交付。

交接：输入：模型输出事件。输出：规范化 opening；新飞书 Session 的入口合入首个有效开场，若没有开场则合入首个最终答复。

等待：内容先形成并保存，投递另走 outbox。首个有效开场不等待完整任务清单。

可见与证据：飞书显示【开始处理】和会话入口；这里首次让人知道模型准备怎样解决问题。

#### 8. 按工作量建立任务快照

Harness / Run → Session / Request；承担者：执行 Harness 决定并验收；平台校验结构；交接方式：sync。

可建卡的工作 Session 中，已启用试验的复杂或长任务，由 Harness 提交目标、2–5 个交付项及验收条件。groupFeed 旁听 Session 被明确排除；短问题若留在该 Session，即使后来调查变长，也不能据此保证会建卡。简单任务不需要卡。

交接：输入：目标、taskId、revision、交付项、证据引用。输出：持久 workboard 快照；续作沿用原 taskId。

等待：提交快照要等待保存；不等待飞书卡片创建成功，工具工作可以继续。Jev 清单 gate 已取消，但它建议的工作位置仍可能影响可建卡范围。

可见与证据：网页可直接投影快照；飞书卡片 Worker 稍后创建一张卡。

#### 9. 投递开场、创建或更新卡

Session / Request → 输出 Worker；承担者：两条独立输出程序；交接方式：async。

开场、问题、最终答复走 source-delivery outbox，由 Connector 调飞书 API。已启用的任务卡由另一 Worker 读 Session 快照，首次 create，后续 patch 同一 messageId。

交接：输入：输出事件或任务快照。输出：飞书 messageId、卡片锚点、内容版本与提供方回执。

等待：两条 Worker 可并行追赶事件，并不共享一个发送队列；事件顺序不等于客户端严格到达顺序。目前跨 Worker 的“开场必定先于卡片到达”没有统一屏障。

可见与证据：这说明为何“模型已经开工”与“卡片刚弹出来”可能有间隔。

#### 10. 飞书显示开场与首卡

输出 Worker → 用户 / 飞书；承担者：文本 Connector 与卡片 Worker 各自发送；交接方式：async。

文本发送和卡片创建从各自持久记录推进。有用开场与首卡可在这里被用户看到；当前没有统一屏障保证二者在客户端严格先后。

交接：输出：开场 messageId、首卡 messageId 与绑定。

等待：不等待后续工具任务完成；发送结果由各提供方 API 回执确认。

可见与证据：这里才是表面交付，保存开场事件或快照本身还不算送达。

#### 11. 进度更新原卡

Harness / Run → Session / Request；承担者：Harness 输出实际发现；卡片 Worker 更新表面；交接方式：sync。

有用进展被标为 progress 并保存。有任务卡时，投影把它合入原卡的进度区，不再为每句话新增群消息。交付项只有验收证据充分时才能打勾。

交接：输入：新的进度事件、同一 taskId 的更高 revision。输出：原卡最新进度与验收状态。

等待：卡片刷新独立于后续模型工作；没有卡时，有用进度仍可能单独显示。

可见与证据：保留一张推进卡，目标在上、交付项居中、实际进度在下。

#### 12. 卡片 Worker 编辑原卡

输出 Worker → 用户 / 飞书；承担者：个人试验卡片 Worker；交接方式：async。

读取新的任务版本和实际进度，对原卡的 messageId 做 patch，并核对提供方响应；创建结果未知时不能盲目再建卡。

交接：输入：已有卡片身份、最新快照和进度。输出：同一张卡的新内容及回执。

等待：模型执行不等这个 patch；卡片可以稍后追赶最新事件。

可见与证据：群里不新增另一条进度消息，也不另发一张全部完成清单。

#### 13. 保存并投递最终答复

Harness / Run → Session / Request；承担者：Harness 写结果；RemoteLab 保存；Connector 发送；交接方式：sync。

Harness 给出本轮结果、已完成部分及真实剩余阻塞。平台标记最终答复，并由 outbox 投递文本和附件。Run 结束、任务验收完成、飞书送达分别记录。

交接：输入：最终事件和已保存资产。输出：独立【最终答复】与分片 / 附件回执。

等待：无需等后置标题整理或记忆归集。投递失败从已保存结果恢复发送，不自动重跑工具动作。

可见与证据：【最终答复】表示这轮回答结束；任务卡仍可以是部分完成、等待或失败。

#### 14. 最终结果进入 outbox

Session / Request → 输出 Worker；承担者：RemoteLab 输出投影；交接方式：async。

从已保存的最终事件建立幂等的文本 / 附件投递记录，供 Connector 领取。

交接：输入：最终事件、资产和原 Request 的回复位置。输出：待投递记录。

等待：任务结果已有，飞书仍可能待发送。后置整理不在等待条件中。

可见与证据：还不能仅凭 outbox 记录声称群里已收到。

#### 15. 飞书显示最终答复

输出 Worker → 用户 / 飞书；承担者：Connector 调提供方 API；交接方式：async。

发送文本及附件，沿原话题或原消息位置交付；各部分使用稳定投递身份。

交接：输出：【最终答复】文本、附件和提供方发送回执。

等待：投递失败恢复本轮既有结果；不自动重做工具任务。

可见与证据：用户获得这轮结果；它可以说明任务仍是部分完成。

#### 16. 保存各部分送达回执

输出 Worker → Session / Request；承担者：Connector + 持久交付记录；交接方式：sync。

保存各文本分片、附件的外部身份和发送状态；卡片 Worker 独立保存自己的卡片回执。

交接：输出：可恢复、可核对的交付状态。

等待：记录全部必要部分的确认，不能用一个成功分片代替整轮交付。

可见与证据：提供方接受不证明真人已读；完整体验仍需要真实入口验收。

#### 17. 后台整理与归集

Session / Request → 后置后台；承担者：独立 Session 状态分类器与记忆流程；交接方式：async。

满足条件时，运行后的状态分类器整理标题、分组和工作摘要，记忆流程另行归集可复用信息。这是后置支路，不是回答前的第二个审查员。

交接：输入：已结束运行的历史与结果。输出：Session 元数据、摘要或记忆记录。

等待：答案投递不等这条支路；它也不能把未验收交付项自动判为完成。

可见与证据：标题或摘要可能稍后刷新；不应再发一遍最终答复。

### 飞书 · 常规接入分支

未启用 Jev observation；Quick 可另用 Jev。常规群不是统一的开关组合。这一分支未启用 jevReactions，但 Quick participation 仍可另调 Jev；等待位置与新的观察快判路径不同。

#### 1. 事件落盘与接入检查

用户 / 飞书 → Connector；承担者：Connector + inbox；交接方式：sync。

可靠保存并去重消息，再检查访问范围、群触发策略、命令以及主线 / 话题路由。ambient 与必须 @ 的群，接入行为不同。

交接：输入：飞书来源事件。输出：可处理消息及其路由。

等待：等待本地保存和结构处理，不等待最终答案。

可见与证据：只有被接入策略接纳的消息进入后续工作。

#### 2. 按该分支尝试收到表情

Connector → 用户 / 飞书；承担者：quickParticipation 或固定 processing reaction；交接方式：conditional。

quickReactions 分支启动已读表情，并发启动 Quick Jev 快判；Connector 只等待已读表情回执，再继续提交工作。另一些配置只把 processing reaction 异步发出。这不是 Jev observation 路径。

交接：输入：消息与分支开关。输出：表情尝试 / 回执。

等待：Quick 分支等表情回执，不等其 Jev 判断；另一些 processing reaction 配置异步发送。

可见与证据：表情与后续任务答复仍是不同证据。

#### 3. 并行的 Quick Jev 快判

Connector → Jev；承担者：旧 Quick participation 的 Jev 调用；交接方式：async。

启用 Quick participation 时，它与已读表情同一轮并发启动，记录参与方式和可能的工作交接建议；建议由 discussionHandoff 接口承接。

交接：输入：有限的群消息上下文。输出：Quick 判定日志和条件发生的交接建议。

等待：Connector 不 await 本次判定完成才提交执行请求；不能把它画成 observation 快判那样的前置串行门槛。

可见与证据：这里也使用 Jev，但当前主模型工作不以该判断结束为启动条件。

#### 4. 接纳可执行请求

Connector → Session / Request；承担者：RemoteLab 接纳层；交接方式：sync。

Connector 提交带稳定 requestId、文本、附件和本条回复位置的请求。结构校验与去重通过后，保存 Request。只有选择 Auto 时，运行档位解析才可能再等待一次 Jev。

交接：输入：sessionId + requestId + sourceContext + sourceDelivery。输出：requestId / runId / queued / duplicate。

等待：调用方等待 HTTP 接纳回执，不等待完整答案。后续运行与 Connector 的这次调用脱离。

可见与证据：接纳成功说明工作进入系统；还不能证明已经开始，更不能证明完成。

交接：输入：已有卡片身份、最新快照和进度。输出：同一张卡的新内容及回执。

等待：模型执行不等这个 patch；卡片可以稍后追赶最新事件。

可见与证据：群里不新增另一条进度消息，也不另发一张全部完成清单。

可见与证据：【最终答复】表示这轮回答结束；任务卡仍可以是部分完成、等待或失败。

### 网页 · 试验 / 常规

同一运行底座，展示按开关。浏览器直接把输入交给当前 Session，绕过飞书 inbox 和群快判。个人任务卡试验是否开启决定展示规则；端口本身不能证明所有人都用了同一规则。

可见与证据：此时才是模型真正承接执行。Session 是持久工作间，Run 是一次运行。

## 运行中用户反馈：当前与目标

### 按停止按钮

当前：RemoteLab 收到控制请求，向原生执行发送 interrupt / cancellation；已做的外部动作不会因此自动撤销。

目标：停止是控制事件，不与问题答案混用；主卡写清取消或暂停及保留结果。

### 文字说“停一下”

当前：目前仍属于普通输入，由 Harness 理解；若正在等原生问题，新文字可能先进入问题答案分支。

目标：在必要的明确停止控制下优先处理；暂停与取消分别持久记录，不自行恢复。

### 插问、补充或纠正

当前：同一运行的兼容输入可送给当前原生 Harness；它判断是否继续、改计划或重新验收。接纳不证明已经采用。

目标：回答插问并说明原任务去向；采用补充后在原卡说明具体变化，改验收标准时重新核验。

### 正在等选择题时又说一句

当前：当前没有附件的普通新文字会自动绑定到 pending native question；并未先可靠区分“回答、插问、停止、补充”。

目标：带 questionId 的答案与普通追加输入分别处理，过期答案不应用；停止不能被吞成自定义答案。

### 问题没有回复

当前：当前统一五分钟：有选项取首项，无选项返回未答；模型收到的是系统超时回退，不能视为用户选择或授权。

目标：可选偏好允许声明默认；必要输入与授权保持待答，无自动默认。

### 原 Run 已结束后再补充

当前：新输入可以在同一 Session 启动新 Run；Harness 判断是否续作，并按规则沿用原 taskId。

目标：问题跨轮持久保留并校验版本，续作编辑原卡，不新建一张“全部完成”卡。

## 真实体验验收

- **复杂任务、无 @**：接入范围内发一个需要调查的问题。核对消息先被观察收录，之后有执行请求；有用开场带会话入口，出现一张主卡，后续进度编辑原卡。 当前边界：真实新任务的完整收发仍待验收。
- **快速问题**：发一个能直接完整回答的问题。应直接得到结果，不补发迟到清单，不为了凑流程拆多条。 当前边界：有代码回归；仍需真人入口核验。
- **插问与补充**：在任务运行中插问，再补充一个改变方案的事实。核对是否回答、是否采用及原任务是否继续，不能只看 HTTP accepted。 当前边界：原生追加底座已实现；体验待验。
- **等待问题时打断**：出现选择题时发“先停下”或一个新问题。观察它是否被当成题目答案。停止按钮与普通文字分别测试。 当前边界：已发现当前分支风险，尚未修复。
- **不回答选择题**：观察五分钟超时回退是否清楚标为系统行为；必要输入与授权不能据此通过验收。 当前边界：当前统一超时策略；分级待改。
- **最终结果与完成状态**：构造只有部分交付项验收通过的任务。最终答复必须清楚说明剩余部分，主卡不能仅因 Run 结束全部打勾。 当前边界：输出标签与状态分离已实现；真实样本待验。

## 开场为什么有信息量

仅复述：收到，我会核对试验端口、常规端口和飞书群，先对照源码，进展和结果放在这里。

已有事实与判断：现有链路把执行停止标成“交付”，普通进度又分散在新消息里。我先拆开任务、执行和投递三种状态，确定各入口要改哪里。

主模型基于本轮已有事实，写出具体判断、关键分叉或首步为何能缩小不确定性。没有核实的发现不伪装成事实；快速完整答案直接交付。开场只承担有用增量，接收表情承担即时确认。

## 异步时序

### 长任务

时间线表示先后与独立承接，不表示固定秒数。发卡与投递不会成为模型开工的前置条件。

1. 用户 → 接入 / 调度：消息到达。真人输入进入已配置入口。
2. 接入 / 调度 → 持久事件：可靠记录 + 去重。同一输入只接纳一次。
3. 接入 / 调度 → 用户：收到确认。飞书表情 / 网页已收到；不等模型。
4. 接入 / 调度 → 执行：启动或续接原生运行。返回接纳身份，执行脱离网页连接。
5. 执行 → 持久事件：开场：有依据的判断与第一步。主模型写内容；不套固定寒暄。
6. 持久事件 → 输出 Worker：开场待投递。确定原会话或唯一工作话题。
7. 输出 Worker → 用户：短开场 + 工作位置。开场不等待完整交付清单。
8. 执行 → 持久事件：任务快照 + 继续执行。目标、2–5 交付项；清单只是展示投影。
9. 持久事件 → 输出 Worker：创建或更新原任务卡。保存卡片锚点和任务版本。
10. 执行 → 持久事件：有证据的进度变化。工具返回、关键发现、步骤变化或阻塞。
11. 持久事件 → 输出 Worker：编辑进度区。合并可读增量；不逐句新增消息。
12. 执行 → 持久事件：验收与正式结果提交。证据支持完成程度；不由 Run 终止猜完成。
13. 持久事件 → 输出 Worker：结果进入独立投递。工作已完成，答复待送达。
14. 输出 Worker → 用户：正式结果 / 附件。保留明确结果标识与完成程度。
15. 输出 Worker → 持久事件：提供方确认回执。全部结果部分确认后才显示已送达。

### 快速完整答复

收到确认之后直接完成并交付；不为开场或任务卡制造额外等待。若卡片尚在准备，终态会阻止迟到创建。

1. 用户 → 接入 / 调度：消息到达。原会话接纳输入。
2. 接入 / 调度 → 持久事件：可靠记录与去重。保存来源与回复位置。
3. 接入 / 调度 → 用户：收到确认。不等待模型判断。
4. 接入 / 调度 → 执行：原生执行。主模型形成完整答案。
5. 执行 → 持久事件：正式结果。无需另交清单和开场。
6. 持久事件 → 输出 Worker：独立投递。取消未发出的迟到卡片。
7. 输出 Worker → 用户：完整答案。原位置直接回答。
8. 输出 Worker → 持久事件：送达回执。任务与投递均有可核对状态。

### 缺关键输入

关键问题没有安全默认。完成独立部分后释放当前执行，待答任务与问题持久保留；回复触发同一任务的续作。

1. 用户 → 接入 / 调度：原任务输入。消息已接纳。
2. 接入 / 调度 → 执行：执行现有部分。先完成不依赖用户回答的工作。
3. 执行 → 持久事件：必要问题 + 等待范围。主模型说明缺什么、为什么、阻塞哪项。
4. 持久事件 → 输出 Worker：保存待答问题并投影。问题归属 taskId / questionId / 对象 / 版本。
5. 输出 Worker → 用户：单独交互卡。主卡显示等待补充，已有结果保留。
6. 执行 → 持久事件：结束本次执行，任务仍等待。不自动首选，不维持空转 Run。
7. 用户 → 接入 / 调度：用户稍后回答。可以在断线或本次执行结束后返回。
8. 接入 / 调度 → 持久事件：校验问题与版本。过期问题不直接应用到新要求。
9. 接入 / 调度 → 执行：续接同一任务。新执行消费答案，不是另造任务卡。
10. 执行 → 持久事件：原卡更新 + 继续验收。等待解除，交付项依新证据推进。

### 结果发送失败

工作与交付分开：投递失败只补投递。结果已产生，不再启动模型重复工具和外部动作。

1. 执行 → 持久事件：验证完成 + 结果保存。工作已完成，有可恢复的结果与资产。
2. 持久事件 → 输出 Worker：结果待发送。沿用稳定 publication / 分片身份。
3. 输出 Worker → 持久事件：发送失败或状态不确定。记失败原因；不确定时先读回，不盲目重发。
4. 持久事件 → 输出 Worker：恢复补投递。只重试需要的结果部分，不重跑任务。
5. 输出 Worker → 用户：正式结果送达。用户获得原结果。
6. 输出 Worker → 持久事件：读回并确认回执。全部部分确认，主卡再显示答复已送达。

## 用户反馈与提问

明确停止优先；结构化问题答案核对任务、题号、对象与版本；其他自由文本进入原生会话，由主 Harness 理解。停止不能被当自定义答案。插问直接回答并继续原任务；补充被收录不等于已采用，采用后具体说明变化；纠正标准后重新验收。独立新目标说明旧任务安排。暂停等待明确继续，取消不自行重启。正式交付前的关键纠正先校验，交付后续作保留版本记录。

- **可选偏好**：能不问就说明假设继续；确需询问时明确默认与采用期限。独立工作继续，默认五分钟后用已告知选项。 未回复：系统默认，非用户回答。
- **必要补充**：说明缺什么、影响哪项。受影响部分等待，其他部分继续；独立工作结束后释放本次执行，保留待答任务。 未回复：等待回答；不自动首选。
- **明确确认**：列明动作与影响，只等待必要决定。已有授权的日常工作不重复求确认。 未回复：没有同意就不执行该动作。

当前普通选择题五分钟后默认首项；该现状不满足必要输入与授权的分级目标。必要待答任务可释放本次执行，但持久保留问题；稍后答案续接同一卡片。

## 三种独立状态

- **任务 / 工作卡**：进行中 → 等待补充 / 用户暂停 → 进行中 → 已完成 / 部分完成 / 失败 / 取消。维护者：Harness 给出验收事实，平台保存。同一任务可以跨多个 Run。现有 workboard.status 保留；拟增加 waiting.kind 区分必要输入与用户暂停，不能仅由 Run 终态宣布完成。
- **一次执行 Run**：已接纳 → 运行中 → 执行终态 → 按新输入续接下一次执行。维护者：原生 Harness 与运行宿主。已接纳不等于正在执行；结束本次执行可以留下待答任务。停止确认和任务取消分别记录。
- **结果投递**：尚无正式结果 → 结果待发送 → 发送中 / 失败待恢复 → 回执确认已送达。维护者：publication / outbox Worker。工作完成不等于答复送达。发卡、答案、附件和分片须有各自回执；不确定发送先读回。

## 交接契约（规划名称，非现行 API）

- `message.received`：接入层 写入 消息已可靠记录与去重；接收确认器 / 会话调度 消费。事件名为规划，不是现行 API。
- `input.accepted / input.applied`：原生桥接 / Harness 写入 通道已接纳 / 主模型已采用，分别记录；运行观测 / 进度区 消费。已有接纳底座；采用展示待补。
- `assistant.opening`：主 Harness 写入 有信息增量的判断、第一步与输出归属；开场投影 / 工作话题入口 消费。内容职责与合并规则待落地。
- `task.snapshot`：Harness 提交；平台结构校验 写入 taskId、revision、goal、items、progress、waiting；Web / 飞书原卡投影 消费。拟扩展现有 workboard 快照。
- `question.opened / answered`：Harness 定义；问题 Broker 存储 写入 questionId、等级、对象、任务版本、未答政策及回答来源；交互卡 / 当前或下一次原生执行 消费。分级与持久待答待补。
- `result.committed / delivery.confirmed`：Harness 验收 / 投递 Worker 写入 正式结果与完成程度 / 提供方确认的回执；结果消息 / 卡片答复状态 消费。复用现有出版与投递底座。

## 改动与真实入口验收

### 接收与开场

承担者：接入层 + Harness + 输出适配器。

现状：Jev 试验分支先快判再提交，表情排在之后；会话入口已合入有内容的开场，无固定创建通知。

改动：可靠收录后前置确认；主模型给有依据的开场；群内开场同时作为唯一工作话题入口。

验收：无 @ 的接入消息能确认收到；未接单不假报开工；快速答案不会被迟到开场和卡片打断。

### 一张任务卡承载进度

承担者：Harness 写事实；持久层与 Web / 飞书投影。

现状：卡片有目标、验收项和总体状态；进度区已实现，同一任务更新原卡；可建卡 Session 中由执行 Harness 判断；groupFeed 旁听 Session 被排除。

改动：扩展 progress 与 waiting；标题用目标；按真实变化更新原卡，保留必要历史。

验收：同一 taskId 跨 Run 仍是一张卡；普通进度不产生新消息；重连恢复最新版本，不重发旧历史。

### 分级问题与续作

承担者：Harness 定等级；问题 Broker 保存与路由。

现状：普通有选项提问五分钟后默认首项；必要性没有单独字段，表面仍是问题文字。

改动：交互卡注明级别、未答政策、影响范围与对象；必要问题持久待答，不超时强选。

验收：必要补充无回复保持等待；可选题的默认标记非用户回答；跨 Run 的迟到答案正确接回原任务。

### 停止、插问、补充与纠正

承担者：原生输入通道 + Harness + 结构化控制。

现状：已有原生追加输入和停止底座；存在待答问题时把新文字作为候选答案的路径。

改动：停止控制优先，答案绑定具体问题；自由文本交给 Harness 分类处理，实际采用后写进度。

验收：待答时说停止不被吞成答案；插问不结束任务；纠正影响的标准重新验收，收到与采用可区分。

### 完成与送达分别展示

承担者：Harness 验收 + publication / outbox Worker。

现状：已有独立投递与回执底座；开场、问题和最终答复分别标识；最终答复不宣称任务完成，结束后不补发新卡。

改动：明确正式结果输出意图和完成程度；卡片同步工作状态与答复状态，竞态中阻止迟到创建与过期结论。

验收：Run 结束不自动宣布成功；发送失败只补投递；结果前有新纠正先校验，结果后续作有修订记录。

## 不变边界

- 接收确认不等待模型；收到不冒充已理解或已开工。
- 主 Harness 是唯一任务理解与验收者；不增加隐藏 planner 或独立卡片模型。
- 同一任务在 Session 中保留稳定身份；Task 卡是投影，不另造全局任务产品。
- 普通自动进度更新原卡；用户主动提问仍直接得到回答。
- 必要输入与真实授权不会因无人回答而默认同意。
- Run 结束、任务完成、结果送达分别有证据；互不替代。
- 原生输入或外部发送结果不确定时先核对，不靠重复执行消除不确定。
