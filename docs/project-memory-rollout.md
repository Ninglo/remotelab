# 全范围项目记忆：在原流程上增强，真实使用后调优

可以把下面的话交给负责当前实例的 Agent：

> 沿原项目主账、来源采集和日报启用项目记忆增强，覆盖全部已登记项目。先核对服务、现有改动、来源和缺口，冻结旧代码及相关内容；建立项目章节索引和明确群／Session 关联。不要加第二本共识、第二个消费者或额外模型规划器。验证新旧线程的实际准备路径和关闭恢复，交付源码、核验当前服务，然后用真实开工、日报和人的纠正判断效果。缺口继续记录，不等全部角色登记或离线评测结束才推开。

该推进方式来自2026-10-03用户对本治理的明确要求，覆盖旧方案“离线对照通过才接入”的先后顺序。仍须区分实际证据、人的认可与效果；记忆增强不扩展业务动作或额外消息发送的授权。

## 与现行机制的实际差别

现有日报已经读取群讨论、追溯相关 Session、更新唯一项目主账，再按原出版器交付。本轮复用这些工作，只增加：

- 精确来源群／明确 Session → 项目 ID → 同一主账章节的指针；新的普通线程和原生续接均能收到当前版本。
- 原日报读取同一登记范围及版本规则，补归属、来源和纠错；普通可核实事实沿原位置更新，重大责任和验收变化找相应人反馈。
- 冻结基线、运行版本／配置 hash、总开关及两项独立关闭，让增益可以停用、问题可以追溯。

运行模块不读业务正文，不判断项目优先级，不把摘要当执行证据。Harness 仍决定这次读什么、怎样理解、如何更新。未匹配的请求不新增项目块，仍可按原 projects.md 在明确需要时导航。

## 存储与运行开关

默认配置位置是 `~/.remotelab/memory/project-runtime.json`；实例可用 `REMOTELAB_MEMORY_DIR` 覆盖。它是可选的后台导航配置，不是新的交互式项目产品。配置缺失、损坏、超出64 KiB或关闭时，普通开工路径继续。

```json
{
  "schemaVersion": 1,
  "enabled": true,
  "contextEnabled": true,
  "reviewEnabled": true,
  "releaseId": "v1",
  "indexPath": "/private/project-knowledge/project-index.md",
  "ledgerPath": "/private/project-knowledge/projects.md",
  "workflowPath": "/private/project-review/project-memory/releases/v1/workflow.md",
  "projects": [{"id": "example-project"}],
  "groups": [{"sourceRouteId": "example-bot", "chatId": "example-chat", "projectIds": ["example-project"]}],
  "sessionBindings": [{"sessionId": "explicit-example-session", "projectIds": ["example-project"]}]
}
```

这是虚构配置。真实群、人员、资料与基线留在认证实例，不随源码或公开网页发布。项目索引只存项目身份、父子关系和章节入口，不复制状态。主账继续在原 `project-knowledge/projects.md`；原消息、工具结果、来源截止时间、覆盖缺口和投递回执各留原位置。

`chat/project-memory-runtime.mjs` 校验配置，在 `chat/turn-context-hook.mjs` 投影一段紧凑 metadata。匹配以本轮 `sourceContext.sourceRouteId + chatId` 或明确的 `sessionBindings` 为准，不用标题、sidebar、Person 或共享用户名猜。明确的本轮来源覆盖旧会话来源；该群关联优先于 Session 的默认关联，跨项目的具体事项仍由 Harness 判断。本轮上下文只提供入口，正文是否被使用须看真实读取和任务证据。`bare-user` 等明确不使用 manager context 的路径不强加这段配置。

原日报调度提示按 `enabled && reviewEnabled` 读取版本规则；普通指针按 `enabled && contextEnabled` 投影。日报开关通过既有调度提示执行，仍由 Harness 遵循，它不是 OS 写权限限制。每轮记录配置版本、hash、来源与主账版本。后续规则用新 release 路径保留旧版，不能改写已冻结规则来冒充原版。

## 怎样确认有用

三种验证各回答不同问题：

| 验证 | 能确认什么 | 不能用来代替什么 |
|---|---|---|
| 原消息、工具结果或业务系统 | 事件和实际状态、来源时间 | 负责人认可、项目效果 |
| 项目负责人、相关个人、验收人反馈 | 范围、责任、承诺和验收是否认可 | 没回消息不能当同意 |
| 真实任务与日报纠错记录 | 找对项目、少漏报、纠错传播、是否改善协作 | 两份摘要读同一来源不能独立验证事实 |

冻结旧版用于解释差异、重放和定向修复；它不证明旧认识全部正确。离线同题对照是需要时的诊断工具。先真实使用，再逐类记录成功、错误、漏报与人工负担；前台 token、文件读取、第一条有用回应和后台成本分开观察。现有 token 账本不能自动把 token 精确归到每份记忆，因此不要填虚假的节省比例。

## 关闭与恢复

修改配置时先读当前内容，只变对应开关，原子写回；保留其他字段和来源关联。`enabled=false` 关闭全部增强；`contextEnabled=false` 只关开工指针；`reviewEnabled=false` 只关原日报新规则。无需再次修改群消费者或日报日程。关闭后原路径继续，新的有效项目事实仍保留。

代码冻结与内容快照分别记录准确版本和 hash。发现错误用对应提交、条目及来源定向更正，不把整本旧快照覆盖回去而删掉别人后来的工作。配置停用不能清除原生线程已读记忆；必要时新建原生线程并重读旧入口。已经启动的日报也可能保留旧规则，需要按本轮实际读取记录判断，不承诺即时擦除所有运行上下文。

这轮没有改持久存储 Schema、创建新的消费者或日程；回退平台代码仍须核对同期其他变更，不能以本功能关闭代替整个源码安全回滚。准备工具里的 `prepared` 描述离线准备工作，不是在线增强的权限门禁。

## 验证与边界

`npm run test:memory-governance` 验证原隔离采集和新增配置路由、真实 `buildPrompt` 新旧线程投影、关闭及坏配置恢复；这些测试不启动供应商模型。还需核对主线 CI、实际服务 commit、当前配置，以及真实后续 Harness 读取与日报反馈。提交或 prompt 准备成功均不能独自证明全部协作效果。

登记节点可能含组合、子项目、探索、暂停和历史主题，不称为同等活跃项目。未知群、未声明个人 Session、角色和附件覆盖仍逐项补齐。旁观者观察的好方法先保留原例子与复用证据，不能自动成为 Skill、排期或执行授权。个人偏好、公司事实和原自动候选写回是独立工作，不随此开关宣称已完成。
