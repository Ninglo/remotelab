# 分阶段判断价值

生成前 actualUtility=unknown，判断是否值得投入制作；不要将 unknown 计零，也不要预估成已实测的高分。85分是质量目标，未经真实样例校准不使用伪精确总分。

确认制作时先写本条 Skill 的价值假设和通过条件。例如“面对混合有效样本，能识别 reduction 造成的不可比，并算对有效样本平均值”；不能只写“回答更专业”。

## 独立验证

1. 保留产生该经验的案例用于理解，另选未参与编写的新输入验证；再加一个相近但不适用的反例。测试材料不能把标准答案塞进提示。
2. 用相同模型、配置、任务和可用工具对比无 Skill 与有 Skill，使用隔离上下文，避免先看标准答案再跑基线。已存在相近 Skill 时应比较现行版与修改版。测试应有代表性；单次成功不足以证明稳定优势，结果波动时补合理重复或标不足。
3. 保存实际提示、模型条件、Skill 版本、原始产物、命令及回执、耗时与可得的 token 用量。无法取得某指标标未知。
4. 按预先标准比较任务成功、事实/计算错误、遗漏、人的返工、触发准确性和成本。人的满意度是证据之一，不自动成为因果增益。模型自评不能代替有正确答案的计算检查或人的实际使用判断。

建议评价结果分 confirmed-gain / no-demonstrated-gain / regression / insufficient-evidence，逐项带依据与覆盖范围。生成前、草稿检查、试用效果分别保留，不能只留最终总分。严重错误或不满足权限/任务边界不能靠其他得分抵消。

验证环境和成本在候选范围内；不为测 Skill 启动训练、部署、发送群消息或改变外部业务。必要高成本验证缺少授权时保留待测项。

## 输出与使用

evaluation.json 至少包含 candidateVersion、skillHash、hypothesis、criteria、cases（输入、基线/Skill产物与证据位置）、verdict、limitations。没测的标未测，不写通过。

包装和可执行性通过且无已知严重错误，可交本人有限试用；如果效果尚未显示优势，明确写“尚未证明增益”。有反例则修订或停用；不要每天自动重测所有 Skill。首次有效结果也不自动公开，试用结束后沿本人决定处理。
