# 一键状态升级工具

供旧 Request 格式实例升级使用。工具统一转换规则、对账、数据切换、恢复记录和回滚；每台机器的服务名、端口及代码切换命令放在一份计划文件中。运行中的任务默认阻止升级，工具不会主动中断它们。

把下面这段交给负责目标机器的 AI：

```text
请使用 RemoteLab 的 upgrade-state 工具迁移这个旧实例。
先按 docs/request-state-upgrade-plan.example.json 准备这台机器的升级计划，
保存可启动的旧源码、依赖和服务配置，并准备新版本及其依赖。
新版本须包含本工具及 request-state-upgrade.md 列出的修复。
请核对所有输入消费者、connector、定时任务和独立存储路径，生成并检查服务命令。
不要把活跃服务的共享代码树直接更新掉；先准备可切换的新源码。
在目标服务停止后仍可工作的终端或维护进程中执行；正在运行的任务等结束。
按同一份计划完成升级，返回转换数量、ID 映射、待核对项、健康检查和备份位置。
真实飞书回发和重启验收单独标明结果，不用端口在线代替。
```

此入口用于从可验证的旧版本升级；旧服务已经故障时，先恢复匹配的旧代码/配置，或在停写备份上使用离线转换器排查。

机器信息由 AI 从服务配置收集；缺少服务权限或必须明确处置正在运行的业务时，再集中向操作者询问。无需让人逐条执行迁移步骤。

## 一个执行入口

从准备好的**新版本源码**运行（旧版 CLI 尚无此命令）：

```sh
node /prepared/new-source/cli.js upgrade-state apply --plan /prepared/instance-plan.json
```

意外中断后重复同一命令即可读取进度继续，不新建另一份升级目录。查看记录或请求回滚：

```sh
node /prepared/new-source/cli.js upgrade-state status --plan /prepared/instance-plan.json
node /prepared/new-source/cli.js upgrade-state rollback --plan /prepared/instance-plan.json
```

`workDir` 必须是尚不存在的新目录，父目录需已存在；计划与服务适配脚本放在独立的 prepared 目录。

计划样例见 [request-state-upgrade-plan.example.json](request-state-upgrade-plan.example.json)。`OWNER`、路径及版本号都是待替换值，不能照抄执行。

## 固定执行流程

1. 校验计划，获取实例级独占锁。计划与工作目录绑定；再次执行不能换一套参数。schema 1 实例返回 `already-migrated`，不重复转换，也不声称已做真实收发验收。
2. 首次执行先核对旧服务的认证和运行版本，再执行预检，在副本上完整试转并对账；失败时服务尚未停止。试转检测到源文件变化时也会失败，应安排输入平静的时间重试，不能忽略变化强行使用副本。
3. 按计划停止服务，检查停止结果和遗留执行进程，再重新取得最终数据并转换。工作目录须与数据目录在同一文件系统。
4. 对照原数据验证全部运行 ID、Request 索引与结果状态、会话元数据、排队输入、发送记录、旧去重记录；历史、附件和其他应保留文件逐文件检查 SHA-256。
5. 保留旧数据为 `backup/`，用已验证的 `staging/` 替换实例目录；切换代码/服务配置并启动。使用实例自己的 token 检查登录接口、会话接口和实际运行提交，再检查 connector 状态。
6. 返回 `migrated` 和各项数量，`liveE2E: not-run` 明确保留。原聊天收件及任务执行中重启测试，仍按[升级验收说明](request-state-upgrade.md)执行。

## 一致的转换规则

- 每条历史 Run 都保留原 `runId`。共享 request/response ID 时，明确的 publication root 优先，其次按创建/启动时间和 Run ID 固定排序选定原 ID 的拥有者；其他记录得到确定的新 ID。`identityMappings` 与记录中的 `legacyIdentity` 保存前后映射。已有调用者若依赖某个旧共享 ID，应按映射核对语义；不能把一个共享 ID 当作多次运行的独立地址。
- 旧 handled 记录导入每个机器人的新 Inbox。缺少可靠 handled 回执的旧入站事件保留在 `migration-review.json`，并占住去重 ID；它们不会自动启动任务或重发。操作者按清单核对后决定如何处理，工具不会把“未重放”冒充“已经完成”。
- 旧发送中的记录转为 `unknown`，旧失败发送转为 `delivery_failed`。历史普通回复、邮件和日历等完成后动作不自动重做。
- 自动发现实例内的默认机器人、多机器人配置和 registry 中的配置。支持外置的绝对 `storageDir`：复制进新实例目录并修改对应配置，原外置目录保留；回滚使用旧配置和原目录。两个机器人不能共享同一存储根。
- 旧 `intakePolicy` 转为 `accessPolicy`，保留已有 sender 白名单；移除当前版本已不再接受的旧配置项。未指定群响应方式时采用 `mention_only`，配置变化记录在报告。原群审批、动态成员授权等旧语义不再提供，升级前应阅读该配置差异。
- 不明确的批量历史身份、排队输入身份冲突、未处置的旧 completionTargets、半成品 Request 存储、相对存储路径、实例外的机器人配置、软链接和不支持的配置会使转换失败；不会靠删记录跳过。先整理这些输入再重试。

## 计划中的机器适配

`commands` 是按顺序执行的 argv 数组，不经过隐式 shell。对象形式支持 `exitCode` 和精确的 `stdout` 断言。各命令必须可重复执行并等待其子进程结束，不能后台派生未跟踪的操作，不能包含业务消息发送。

- `preflight`：验证新旧代码提交、依赖和服务备份均已准备好，权限可用；不要在这里切换代码或停止服务。
- `stop` / `stopped`：停止并检查**这个实例的全部写入方**，包括独立 connector 和调度入口。示例 systemd 命令需要按实际 unit 列表展开；macOS 可提供相应 launchctl 命令。
- `activate` / `restore`：分别安装新/旧源码入口及完整服务配置。保留匹配的依赖；Linux 同时处理实际 unit 的 runner scope 和 `KillMode`。工具不替你猜这些路径，也不会执行全机器的 `git pull` 或重启所有实例。
- `start`：启动所选实例的服务；恢复旧配置后也调用这组命令。
- `connectorsHealthy`：对当前实际运行的版本检查 connector；使用本次启动的连接证据，不能只搜索历史 ready 日志。这组检查也用于回滚验收。HTTP 版本检查由工具另行执行。

升级必须以实例数据的所有者身份运行，数据目录权限随转换保留。命令继承当前用户权限，实例环境变量被限定为计划中的数据目录和端口；没有自动提权。计划及适配脚本应在停机前保存到独立维护入口可读取的位置，并先检查原数据及旧代码的恢复能力。共享源码的其他实例须单独安排，不能被 `activate` 顺带升级。

## 失败、继续和回滚

`upgrade.json` 每步落盘；`plan.json`、转换报告、源文件清单和私有命令日志保留在工作目录中。不要编辑原计划后复用同一目录，也不要删除 `backup/` 或盲目清锁。

- 转换或启动检查失败时，工具尝试恢复数据及旧代码。只有旧版本 HTTP 和 connector 检查通过，才记为 `rolled_back`；否则记为 `rollback_failed`，退出失败，继续保留现场。
- 新数据相对安装时有变化时，自动回滚会停在 `recovery-required`，避免覆盖新增工作；需要对账后处理。此检查故意保守，启动时新增的配置/日志也可能触发它，不能为了回滚方便绕过。
- 重复 `apply` 可继续已记录的切换步骤。若原转换子进程仍活着，等待其结束再继续；执行归属无法判明、锁文件写入不完整或回滚途中状态不明确时，工具明确停止，不能猜测并发进程已经结束。
- 工作目录包含数据备份、机器人凭据及私有日志，应按敏感实例数据保管。仅分享脱敏后的数量和结论。
