阅读指南 / 统一说明版 · 2026-10-03

把事情讲明白，
也把系统讲清楚。

RemoteLab 把对话、机器执行和持续工作的记录接在一起。这份说明从你看到的事情出发，继续解释谁负责、文件在哪里，以及下一次怎样接续。

你可以只沿正文理解工作，也可以展开交接数据、存储格式、源码和验收依据。两种读法使用同一份内容：解释不会停在比喻，技术细节也不会取代事情本身。

本轮统一的是说明结构与 UI。各机制沿用自己的来源、核对日期和实现状态；网站修订日期不代表所有运行能力重新验收。

01 / 两层读法先知道发生什么，再知道怎样做到。

每个主题的正文先回答一个实际问题，例如“发来的消息有没有被收下”“任务还在执行吗”“写进记忆后，下次会不会使用”。然后按理解所需的顺序解释触发条件、负责组件、输入输出、先后与并行、结果和例外。

涉及实现时，展开项保留字段、文件、接口、调用关系和来源。左侧的“展开研发细节”可一次打开这类说明；“逐节阅读”恢复按需展开。功能演示、假设试算和真实记录仍各自标明性质。

研发读者应从说明里查到哪些信息？

从用户动作追到 Request 与 Run，从组件职责追到输入输出，从持久状态追到文件或接口；还要能分清程序写入、模型生成、人的确认和下一轮读取。源码链接使用该条目的核对基线；复核运行状态时，另查实例 build-info、配置、业务记录与实际回执。

本文中的配置目录和记忆目录是逻辑位置。通常分别为~/.config/remotelab与~/.remotelab/memory，可由实例环境覆盖。公开网页解释结构；完整实例路径和个人资料只在登录后主动读取。

02 / 按问题进入三个章节，一条共同主线。

系统如何工作 →

认识对象、事件和状态；按输入路径与机制索引找到实现。

一次工作如何执行与交付 →

沿消息接入、任务执行、运行中反馈和结果交付继续查到记忆。

记忆如何保存与接续 →

项目、人员、公司分别存什么，下一轮怎样读取，人的纠正如何回来。

只查文件：去完整文件地图。只查当前实例：去登录后的按需读回。目标交互与可操作示意保留在演示附录，不会混成当前运行事实。

03 / 先认识对象对话、请求、执行和交付各有职责。

这些名字描述工作的不同部分。发来一条消息，可能只被记录，也可能产生一次执行；一次执行结束，结果还需要验证和交付。

Session · 工作话题
持续保存一段工作的对话、状态和恢复入口。它可以包含多次输入、多次执行；它的创建者不能代替本轮消息作者。
Request · 一次请求
把本次输入及其来源、回复位置、执行选项固定下来。消息已收录与请求已被执行调度接纳，是两个不同的交接点。
Run · 一次执行
运行 Harness 和工具，留下状态、日志、结果与产物。Run 结束只证明这次执行结束，任务是否完成要看实际验收。
Harness · 执行工具
例如所选的 Codex、Claude 或 Pi。它理解任务、规划、使用工具并判断验收；RemoteLab 提供传输、机器运行和持久上下文。
Connector · 外部接入
连接飞书等来源，接收和路由消息，再把结果送回原请求的位置。接收记录、Session 关联和外部投递分别留痕。
Person · 已核人员
用于本轮作者归因、个人视图和相应偏好选择。它不是 Session 的访问隔离；共享机器用户名也不是人的身份凭据。

04 / 完整机制一次工作，沿六个交接点走。

  1. 收下输入，留下来源。

    网页或连接器接收消息，保存相应事件和来源。群快判、命令或不同入口有各自分支；不是每条消息都会启动模型。

  2. 关联工作话题，接纳可执行请求。

    先区分写入 Session 历史与提交 Request。执行选项、原输入及结果应回复的位置随请求保存，避免后来输入改变旧结果的去向。

  3. Harness 理解任务，使用机器和工具。

    Run 独立推进。同步交接需要等当前回执；异步分支继续推进，但仍有自己的依赖、失败记录和完成条件。

  4. 处理补充输入与需要你回答的问题。

    停止、插问、补充条件和问题回答是不同意图。输入被可靠接纳，还需要实际执行采用它，再检查受影响的结果。

  5. 验证工作，再交付结果。

    任务卡表示工作验收，投递回执表示结果送达，Run 状态表示执行状态。三者可以不同，不能互相替代。

  6. 整理候选，按用途保存，下一轮按需读。

    原始过程留在来源；已确认的项目事实回主账，人员偏好与公司背景各回原档案。候选仍待核，指针帮助下一次找到相关内容。

具体数据、等待条件和分支见交互时序；不同事件怎样修改状态，见状态地图。

从一次编辑到发布，具体经过哪些步骤？
  1. 修改原内容源；生成型README运行对应render-reference.mjs更新。普通维护README直接编辑。
  2. 运行node docs/architecture-atlas/assemble-site.mjs <空输出目录>。它复制允许的静态资产，重写外置记忆章的相对路径，并从同一目录生成五个页面的通用导航。
  3. 检查链接、章节交互、桌面和手机阅读、无脚本导航与公开信息边界，再按仓库main／CI规则交付。
  4. 使用remotelab publish static --source <输出目录> --slug remotelab-architecture-atlas --replace --json覆盖原网站，匿名回读实际页面。
  5. 保留source/、site/、manifest.json、SHA256SUMS与RESTORE.md；从备份恢复后重新构建，核对输出一致。

JavaScript 数据文件是说明的数据源，不是记忆数据库。Markdown是可维护、可供Agent阅读的文本，JSON是结构化配置，JSONL是逐行事件流；文件格式与项目／人员／公司归属是不同的问题。

06 / 从使用走到研发用一个真实问题，走完整条路。

新读者先把“一条消息”走完，知道接入、执行和交付分别发生什么；再看系统总览里的状态位置；最后看记忆怎样让后续工作接续。维护者可以反过来，从具体问题和文件定位开始。

  1. 消息是否收下、执行是否开始？沿两次交接查Request和Run，不把收录当成执行。
  2. 工作完成，为什么还没看到结果？分别查任务验收与投递回执，保留原请求的回复位置。
  3. 这件事记住了，下一次会不会读？查正常指针、当前身份和项目范围，再核对实际读取。

07 / 事实与验收状态要说明“证明到了哪一步”。

源码已核证明代码里有实现；配置已核证明某实例某时刻的设置；运行样本证明一条具体链路发生过。目标方案和待核项继续明确标注，不因图画得完整就变成上线事实。

反馈推动改进：先描述用户遇到的事情，再沿链路定位责任，修改后验证受影响部分，最后更新同一章。旧样本保留日期，被替代的判断保留原因；任务状态和业务事实仍回原系统维护。

哪些验证需要分开做？

代码测试、部署版本、真实输入、工具或业务结果、外部回执，以及用户是否按结果完成目的，分别有证据。只改说明网站时，检查文档和网页的交付；不把它说成无关运行功能的验收。

08 / 持续维护后续更新，沿同一套写法和 UI。

已有主题更新原章；确需独立主题，登记到同一目录、复用通用 UI、进入同一发布包和备份。术语首次出现解释含义，正文先说明事情，研发细节继续完整保留。

通用规范维护在项目README，通用样式维护在guide.css。各章自己的样式只承接图、表和演示布局，不再另定一套颜色、标题或导航。
