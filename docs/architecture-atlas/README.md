# RemoteLab 整体说明项目

这个网站是 RemoteLab 的长期说明项目：帮助我们梳理系统全貌、根据真实体验持续自优化，并让新人快速了解和适应。它从已有架构图谱扩展而来。**后续类似功能说明统一补入本项目，维护同一个目录、阅读入口、发布包和项目备份。**

- 项目 ID：`remotelab-system-guide`。
- 网站总入口：[`project.html`](project.html)；公开入口为 <https://zhangyu.jiujianian.dev/public-pages/remotelab-architecture-atlas/project.html>。
- 唯一维护入口：本文件。机器可读章节目录：[`project.json`](project.json)。
- 归集约定生效：2026-10-03。各章仍保留自己的核对日期、源码基线、实现与验收边界，不能把项目登记日期当成全站内容已经更新。

## 章节与源码

| 章节 | 唯一编辑位置 | 统一发布后的路径 |
| --- | --- | --- |
| 项目目的、阅读路线和目录 | `docs/architecture-atlas/project.html`、`project.json` | `project.html` |
| 系统总览：事件、状态、输入路径、机制与资源 | `docs/architecture-atlas/` 原图谱文件 | `index.html` |

| 记忆与组织协作 | `docs/memory-architecture/` | `memory/index.html` |

消息阅读页09–14同时解释开工记忆、存储分类、项目进程、个人／公司背景和登录后的真实只读视图。正文数据维护于外置记忆章的 `reader-data.js`、`guide-data.js`，`output/memory-reader.js`引用同一源；构建器只重写章间相对路径，不再手工复制内容。

记忆章节沿用原源码维护位置，由 `assemble-site.mjs` 纳入同一网站。发布目录中的 `memory/` 是构建产物，不能在源码中再复制一份独立维护。原记忆网站地址保留历史兼容；新的共同阅读、发布和备份以本项目为准。

新人先看一条消息的全过程，再对照系统总览，最后看记忆与持续协作。维护者从真实案例或反馈出发，沿章节定位责任与缺口；修改、验收后更新同一章。反馈和任务状态仍由原反馈记录、任务系统维护，网站解释并引用这些事实。

## 后续功能说明怎么纳入

1. 先查 `project.json` 和现有章节。涉及已有链路的，更新原章；需要独立展开的，在本项目增加子章节并登记稳定 ID、源码和阅读路径。
2. 新章节明确触发条件、承接组件、输入输出、交接数据、先后与并行、用户可见结果、反馈与异常路径；使用可阅读的图和具体例子，沿现有阅读样式展开。
3. 当前实现、配置或运行样本、拟议方案、待验收部分分别标明。源码、部署版本、真实交付证据按需核对，不能用代码存在或静态网站发布代替功能验收。
4. 每章可以有自己的页面和维护文本，但必须回到同一项目导航，并进入同一发布包和备份。不要另外发布脱离目录、重复解释同一系统的功能网站。
5. 代码邻近的 API、安装、运维指南继续在原权威文档维护，本站用链接把理解路线接起来；修改规则或机制时同步更新对应原文档，不复制相互冲突的正文。

## 统一发布与恢复

把下面这段交给负责维护的 AI；路径、实例和源码版本由它在执行时核对：

> 更新 RemoteLab 整体说明项目。先读仓库 AGENTS.md 和 docs/architecture-atlas/README.md，在现有章节或本项目的新章节中完成说明；保留事实、方案和待验边界。构建统一站点，核对目录、章间往返链接、桌面与手机阅读、无脚本时的基本导航，并扫描公开资产。完成相关检查后按仓库规则提交推送，覆盖同一静态 slug，匿名浏览器读回。为本次可交付版本生成含源码、站点、版本清单、校验和与恢复说明的备份。不要重启或宣称验收与说明改动无关的运行功能。

构建入口：`node docs/architecture-atlas/assemble-site.mjs <新的空输出目录>`。这个脚本按目录组合架构和记忆章节，排除执行脚本、隐藏文件和符号链接；输出可直接静态托管的站点与文件清单。新增章节应在目录中登记，并验证它确实进入发布包。

发布继续使用 `remotelab publish static --source <站点输出目录> --slug remotelab-architecture-atlas --replace --json`。发布内容位于当前实例托管的数据目录，和 Git 源码分别维护；以后不能直接把未组合的 `docs/architecture-atlas/` 作为完整项目发布。

一次可恢复备份包含 `source/`（本项目与外置章节源码，保留仓库相对路径）、`site/`（已组合的静态站点）、`manifest.json`（项目 ID、源码 commit、生成时间、公开入口、章节目录）、`SHA256SUMS` 和 `RESTORE.md`。备份只收录本说明项目，不收录应用凭据、群原文或实例数据库。还原后先核对校验和，再从备份源码运行构建入口；`site/project.html` 可直接由静态服务查看，也可重新发布到已确认的实例。

发布前扫描全部静态资产，核对各章链接和资源请求；每次重要交付核对恢复后的文件校验和、构建结果与浏览器阅读。覆盖原 slug 时更新变更资产的查询版本，避免缓存显示旧内容。完整备份放在本地 `project-backups/`，不作为重复的源码副本提交 Git。

## 更新方法

1. 在 `situation-data.js` 更新情形和状态层。每个情形都填用户可见结果、决策与执行、读写层、成本、下一次读取、判断边界和源码；`reads`/`writes` 同时驱动条目交叉链接与矩阵，不要只改展示文字。
2. 在 `journey-data.js` 更新单次输入阶段或入口分叉。每个入口都必须覆盖同样七个阶段，每阶段填齐用户端、处理与判断、持久状态、资源、协议、代码入口及横向对照标记；跳过 Run 时明确写出为何跳过及后续交付。阶段编号只是该入口的阅读坐标，不是全系统时序。
3. 在 `experience-data.js` 更新深入场景、飞书规则、资源快照；在 `atlas-data.js` 修改机制节点、跨轮路径和证据状态。节点 ID 应保持稳定，源码锚点要能打开。
4. 核对源码入口是否仍存在、行号是否有效，再更新页面上的源码基线和日期。实际部署版本与实例配置要单独读回。
5. 使用一条真实案例串联 Request、Run、结果投递和外部回执；只有完整证据才能把“待核验”改成“运行已确认”。
6. 发布前检查所有静态资产，不能包含群 ID、会话 ID、凭据、内部 URL、用户原文或其他不适合公开的实例数据。
7. 覆盖同一公开 slug 时，同步更新 `index.html` 的脚本/样式查询版本和 `app.js` 的数据模块查询版本；`situations.css` 管情形与状态层，`reading.css` 管阅读层，`styles.css` 保留基础与参考视图样式。公网缓存会保留旧资产，不能只替换文件。对已打开旧页的用户，提供带新查询版本的入口 URL。

本目录是静态 HTML、CSS 和原生 JavaScript，可以直接由静态站点服务提供。网站的源码入口指向此版基线，后续更新时需一起调整。
